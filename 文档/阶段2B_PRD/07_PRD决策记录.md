# 阶段 2B PRD 决策记录

版本：V1.4
日期：2026-10-23

## PD-001：一线辅助为主，治理后台为支撑

**决策**：产品主价值在一线售后决策时发生；知识、评测和发布后台负责提供受控依据。  
**依据**：12 条核心任务全部从客户咨询或售后判断进入，知识后台本身不是业务结果。  
**替代方案**：独立知识管理平台、消费者端全自动客服。  
**代价**：首版需要连接两类用户与既有工作流。  
**待确认**：真实组织内一线使用何种工作台，本阶段不设计页面。

## PD-002：首版坚持人工确认

**决策**：系统只生成条件和证据型建议；发送、退换修判断、风险关闭和发布必须人工授权。  
**依据**：R1-R4、S1-S4、K1-K4 均包含业务责任或高风险边界。  
**替代方案**：低风险自动答复、自动退款或自动保修审批。  
**代价**：不能把首版价值定义为无人化。  
**复审条件**：12 条正式任务和未复核专项样本完成评测，且真实业务验证后才讨论自动执行。

## PD-003：风险流程独立且优先

**决策**：R2/R3 从任意未关闭状态触发独立 `ESC`，普通流程暂停。  
**依据**：安全业务原则和 U1/U6。  
**替代方案**：在普通问答内增加高风险回答模板。  
**代价**：流程更复杂，需要明确的安全责任角色。  
**复审条件**：仅可加强，不可降级安全流程。

## PD-004：知识版本与发布版本分离

**决策**：`KB` 管理内容是否可发布；`REL` 唯一管理对外生效、替代、停用和回滚。  
**依据**：阶段 2A 修正项 D2A-011。  
**替代方案**：让知识版本自身保存线上/下线状态。  
**代价**：阅读当前线上状态需要关联有效 REL。  
**复审条件**：不得重新合并两个生命周期。

## PD-005：知识来源拥有独立生命周期

**决策**：`SRC` 使用首次登记、活跃、待复核、已过期、已替代、已撤回和不可访问七态；首次登记为 `SRC_REGISTERED`。  
**依据**：来源可访问性与内容审批是不同风险。  
**替代方案**：只记录来源 URL，不记录来源状态。  
**代价**：来源失效需要影响分析。  
**复审条件**：来源状态不可删除，只能增加更细状态。

## PD-006：评测通过不等于发布完成

**决策**：评测通过后，匹配 LINK 进入 `LINK_PENDING_RELEASE`；CASE 仅当无其他 OPEN/FAILED 链路且至少一条 LINK 待发布时进入 `CASE_VERIFIED_PENDING_RELEASE`，否则保持 `CASE_FIXING`。
**依据**：评测证明质量，不等于发布和业务闭环完成；一个 CASE 可有多个知识条目修复链路。
**替代方案**：评测通过即关闭案例。  
**代价**：案例需要在待发布态等待 REL 操作。  
**复审条件**：只有 REL 生效或主管与业务负责人联合决定不发布后才能关闭。

## PD-007：P0 分波不缩范围

**决策**：P0 分 W1/W2/W3，正式生产前必须完成全部三波。  
**依据**：安全必须先于知识和发布闭环生效，但完整 P0 仍然需要知识治理和发布。  
**替代方案**：只做 W1 即宣称达到 MVP。  
**代价**：需要跨波回归。  
**复审条件**：波次边界可调整，P0 范围不可缩减。

## PD-008：30 条功能需求覆盖 12 条核心任务

**决策**：将系统能力拆成 30 条可追踪功能需求，每条都至少绑定一个核心任务。  
**依据**：支持需求的业务来源、对象、状态、验收和错误控制。  
**代价**：PRD 与测试矩阵维护成本增加。  
**复审条件**：新增需求必须通过追踪矩阵和核心任务映射。

## PD-009：AI 预填样本不进入正式评测

**决策**：正式评测仅使用阶段 1B `v1.1` 的 12 条人工确认核心任务；24 条 AI 预填样本只作探索。  
**依据**：阶段 1B 有条件验收结论。  
**代价**：首版评测覆盖面有限。  
**复审条件**：专项样本完成人工复核、版本升级和验收后才可加入。

## PD-010：不锁定技术实现

**决策**：PRD 只定义 API/外部系统边界和错误行为，不决定模型、向量库、Embedding、切片、Top K、Rerank 或部署方式。  
**依据**：本阶段没有同条件技术验证和真实数据基线。  
**代价**：技术方案需在后续阶段单独验证。  
**复审条件**：技术选型必须经过任务集评测和架构评审，不能由本文档直接锁定。

## V1.1 复审修订

以下决策关闭导师独立复核中的 PRD-001 至 PRD-006。

## PD-011：自身状态与跨对象事件彻底分离

**决策**：状态总表拆为本对象自身状态转换和跨对象事件两张表；当前对象不得把其他对象状态写入自身下一状态。  
**依据**：导师问题 PRD-001。  
**实现约束**：跨对象事件必须记录来源、目标、目标初始状态、是否新建、幂等键、审计和失败恢复。  
**证据**：[03_状态转换总表_V1.1.md](03_状态转换总表_V1.1.md)

## PD-012：知识来源从登记态开始激活，并产生唯一失效事件

**决策**：新增 `SRC_REGISTERED`；只有可访问、标题核验、范围明确、有效期明确和责任人均满足时才进入 `SRC_ACTIVE`。来源失效触发 KB/EVAL/REL 的唯一阻断链。  
**依据**：导师问题 PRD-002。  
**实现约束**：不自动改写历史 KB 或历史 REL。  
**证据**：FR-015、FR-016、V1.1 状态总表 EV-04 至 EV-07。

## PD-013：回滚复制历史 REL 内容生成新候选

**决策**：历史 REL 永久不可变；回滚复制目标 REL 的 KB 引用生成新的 `REL_PENDING_APPROVAL`，重新审批和审计后才可成为新 `REL_ACTIVE`；原故障 REL 进入 `REL_ROLLED_BACK`。  
**依据**：导师问题 PRD-003。  
**实现约束**：回滚目标可为 `REL_SUPERSEDED` 或 `REL_ROLLED_BACK`，但必须来源有效并重新审批。  
**证据**：FR-021、AC-G-17 至 AC-G-21、V1.1 状态总表 EV-12/EV-13。

## PD-014：REL_ACTIVE 的唯一作用域

**决策**：`REL_ACTIVE` 唯一性范围为同一 `tenant_id + environment_id + business_domain_id`。  
**依据**：导师问题 PRD-003；避免多环境或多业务域互相误判，也避免同域出现两个有效版本。  
**实现约束**：切换活跃版本必须通过替代或回滚事件完成。  
**证据**：FR-020、AC-G-22、PRD G-17。

## PD-015：客服主管只读客户上下文

**决策**：客服主管对 `CTX` 只有读取权；一线客服和售后专员可创建新版本。  
**依据**：导师问题 PRD-004。  
**替代方案**：允许主管编辑，但需要独立需求、审计和权限测试；本次不采用。  
**证据**：FR-004、AC-G-16、权限附录 G-06。

## PD-016：风险排除恢复原暂停状态并重校验

**决策**：`ESC` 新增 `paused_from_state`；排除后先重新校验 CTX/EVD/ADV，通过则恢复原状态，否则生成新 ADV 或进入 `ASQ_ASSESSING`。  
**依据**：导师问题 PRD-005。  
**实现约束**：旧建议失效时不得继续发送。  
**证据**：AC-G-23、V1.1 状态总表 EV-01/EV-02。

## PD-017：角色委托移出 P0

**决策**：首版 P0 不支持角色委托或代理审批；需要调整职责时由身份系统变更实际角色。角色委托列入 P1，后续必须独立定义并验收。  
**依据**：导师问题 PRD-006。  
**实现约束**：不得把权限附录中的口头委托当作 P0 实现依据。  
**证据**：PRD 4.3、权限附录 G-05。

## V1.2 导师复审修订

以下决策关闭导师 V1.1 报告中的 PRD-001 至 PRD-004。

## PD-018：EVAL 成功必须原子推进 CASE 到待发布

**决策**：EV-08 在同一原子事件中更新 KB 为可发布、全部匹配 LINK 为 `LINK_PENDING_RELEASE` 并写 `rel_id`、按全部 LINK 聚合 CASE、创建 `REL_PENDING_APPROVAL` 并写审计。
**依据**：导师问题 PRD-001；否则 CASE 会停留在回归中，REL 生效后无法关闭案例。  
**失败处理**：任一对象更新或审计失败时整个事件不提交，避免半成功状态。  
**证据**：FR-019、FR-024、AC-K4-02、AC-G-27、V1.2 状态总表 EV-08。

## PD-019：停用 REL 必须通过独立回滚候选恢复

**决策**：新增 EV-17，从 `REL_SUSPENDED` 创建新的 `REL_PENDING_APPROVAL`；历史 REL 保持不可变，重新核验历史内容、来源、业务批准和评测资格。  
**依据**：导师问题 PRD-001；来源失效停用后必须有受控恢复入口。  
**失败处理**：候选创建失败时当前 REL 保持 SUSPENDED；重复 `rollback_request_id` 返回原候选。  
**证据**：FR-021、AC-G-17 至 AC-G-21、V1.2 状态总表 EV-17。

## PD-020：KB 在提交业务审核后冻结

**决策**：`KB_DRAFT` 仅在首次提交业务审核前可编辑；提交后内容冻结；评测失败进入只读 `KB_EVAL_FAILED`；修复由 CASE_FIXING 创建新 KB_DRAFT。  
**依据**：导师问题 PRD-002；防止同一版本内容变化导致业务审核和评测证据失真。  
**失败处理**：禁止将冻结的同一版本改回 DRAFT 或覆盖。  
**证据**：FR-017、FR-019、FR-023、AC-G-12、AC-G-28、V1.2 状态总表。

## PD-021：所有跨对象事件纳入统一幂等验收

**决策**：AC-G-26 覆盖 EV-01 至 EV-17；EV-16 重复提交不得产生两个 ACTIVE，EV-17 重复请求返回原回滚候选。  
**依据**：导师问题 PRD-003。  
**证据**：AC-G-22、AC-G-26、V1.2 需求追踪矩阵。

## PD-022：文档编号统一

**决策**：SRC 统一为七态；PRD 的发布与回滚测试为 13.3、在线监控为 13.4；事件统一使用 `EV-` 前缀。  
**依据**：导师问题 PRD-004。  
**证据**：PRD V1.2、V1.2 状态总表、本决策记录。

## V1.3 导师复审修订

以下决策关闭导师 V1.2 报告中的发布模型、CASE 关系、来源失效入案、ESC 复发和验收问题。

## PD-023：P0 采用单 KB 版本发布模型

**决策**：一个 `REL` 只绑定一个 `kb_version_id`；`REL_ACTIVE` 的唯一作用域为 `tenant_id + environment_id + business_domain_id + knowledge_item_id`。业务域级批量发布快照列入 P1。
**依据**：避免更新一个知识条目时使同业务域其他知识条目下线。
**字段**：KB 增加 `knowledge_item_id`，REL 增加 `kb_version_id`。
**证据**：PRD 10.1、G-17、FR-020、AC-G-30。

## PD-024：CASE 与 KB/REL 采用 0..N 关联

**决策**：正常知识首次发布允许无 CASE；一个 KB 版本可关联多个 CASE，一个 REL 只绑定一个 KB 版本。EV-08 有 CASE 时推进全部关联 CASE，无 CASE 时只推进 KB/REL/AUD；EV-11 关闭全部满足条件的关联 CASE。
**唯一关联键**：`CASE_LINK(case_id, kb_version_id)`，创建 REL 后补充 `rel_id`。
**依据**：导师 V1.2 报告第二节。
**证据**：FR-019、FR-024、AC-G-27、AC-G-31、V1.3 状态总表。

## PD-025：来源失效必须进入 CASE 闭环

**决策**：EV-04 至 EV-07 完成阻断后，由 EV-18 采用 `SRC:{src_id}:v{n}:CASE:{case_id}` 幂等键同步 CASE：已有未关闭 CASE 进入 `CASE_FIXING`，已关闭 CASE 进入 `CASE_REOPENED`，无 CASE 时新建 `CASE_OPEN`。
**依据**：导师 V1.2 报告第三节。
**约束**：历史 CASE 不被覆盖；已生效的安全阻断不因 EV-18 失败而回滚。
**证据**：FR-016、FR-022、AC-G-24、AC-G-32、V1.3 状态总表 EV-18。

## PD-026：ESC 终态不复活

**决策**：`ESC_CLOSED` 和 `ESC_DISMISSED` 保持终态；同一客户的新风险创建新 ESC，并填写 `previous_esc_id`。删除 `ESC_REOPENED` 作为 P0 状态。
**依据**：导师 V1.2 报告第四节。
**证据**：FR-013、FR-014、AC-G-10、AC-G-29、V1.3 状态总表。

## PD-027：文档收口

**决策**：PRD 第十六章补齐 V1.2.0 变更记录；所有事件统一使用 `EV-` 前缀；发布回滚测试为 13.3、在线监控为 13.4。
**依据**：导师 V1.2 报告文档收口项。
**证据**：PRD V1.3、V1.3 状态总表、本记录。

## PD-028：V1.3 全量复检的完整性修复

**决策**：发布门槛中的 CASE 条件统一为“若存在关联 CASE”；无 CASE 时只推进 KB、REL 和 AUD。移除 FR-019/FR-024 对 CASE 功能的强制依赖，并将 FR-016 的来源变化能力改为只依赖 FR-015，知识版本与发布作为下游消费者。
**依据**：全量复检发现原表述会使无 CASE 首次发布在验收或依赖图中不可达，并形成 `FR-016 → FR-017/FR-020 → FR-016` 依赖环。
**失败处理**：EV-03、EV-06、EV-07、EV-09、EV-15、EV-16 均补充明确失败保持、重试或人工告警路径。
**证据**：PRD 13.2/13.3、FR-019、FR-024、追踪矩阵 V1.3、状态总表 V1.3 EV-03/06/07/09/15/16、`tests/validate_prd_v1_3.ps1`。

## V1.4 导师复审修订

以下决策关闭导师 V1.3 报告中的 CASE_LINK 生命周期和 `previous_esc_id` 字段问题。

## PD-029：CASE_LINK 采用五态生命周期

**决策**：采用 `LINK_OPEN → LINK_PENDING_RELEASE → LINK_RELEASED` 主链路，并允许活动 LINK 进入 `LINK_FAILED`，或经业务批准进入 `LINK_ABANDONED`。
**依据**：导师 V1.3 报告 PRD-001；CASE 需要可验证的修复、发布、失败和明确弃置过程。
**实现约束**：`LINK_OPEN`、`LINK_PENDING_RELEASE` 为活动状态；`LINK_RELEASED`、`LINK_ABANDONED` 为成功/明确终止终态；`LINK_FAILED` 为失败保留态，不得直接关闭 CASE。
**证据**：PRD 10.1/11.3、状态总表 V1.4、异常附录。

## PD-030：不同知识条目可并行修复，按知识条目聚合关闭

**决策**：一个 CASE 可关联多个 `knowledge_item_id` 并行修复，但同一 `case_id + knowledge_item_id` 同时最多一条活动 LINK。CASE 关闭要求无活动 LINK，且每个知识条目的最新 LINK 为 `LINK_RELEASED` 或 `LINK_ABANDONED`。
**依据**：既支持多 KB 修复，又避免同一知识条目重复开链或部分发布提前关闭 CASE。
**替代方案**：全 CASE 单活动 LINK；无法同时表达多个 KB 的修复进度，因此不采用。
**证据**：PRD G-24 至 G-26、11.3、AC-G-34 至 AC-G-38。

## PD-031：历史 LINK 不可改写，回滚和来源失效创建后继链路

**决策**：EV-13 回滚和 EV-18 来源失效不得把 `LINK_RELEASED` 改回活动状态；需要继续修复时创建 `LINK_OPEN`，以 `previous_link_id` 追溯历史。
**依据**：保持发布与问题闭环证据不可变，并让失败或回滚后的新修复有唯一路径。
**失败处理**：后继 LINK 创建失败时保留 CASE_REOPENED/CASE_FIXING 和治理待办，不伪造关闭。
**证据**：PRD FR-021/025、状态总表 V1.4 EV-13/EV-18、AC-G-36/37。

## PD-032：新增 EV-19 处理明确弃置

**决策**：只有 `LINK_OPEN`、`LINK_PENDING_RELEASE` 或 `LINK_FAILED` 可在主管与业务/渠道负责人独立批准后进入 `LINK_ABANDONED`；弃置后按全部 LINK 重新聚合 CASE。
**依据**：为“明确不发布”提供可审计终态，避免通过直接关闭 CASE 绕过未完成链路。
**证据**：PRD FR-020/023、状态总表 EV-19、AC-G-42、权限附录。

## PD-033：previous_esc_id 成为正式且可校验的风险历史字段

**决策**：`ESC.previous_esc_id` 可空、写入后不可改，只能指向同客户已关闭或已排除的旧 ESC，且每个旧 ESC 最多有一个后继；重复后继、自引用、非终态目标和循环链全部拒绝。
**依据**：导师 V1.3 报告 PRD-002。
**幂等**：相同新风险幂等键和相同旧单引用重复提交时返回原 ESC；同键不同引用或其他新 ESC 引用同一旧单均拒绝。
**证据**：PRD 第十章、FR-013、EV-01、AC-G-29/39/40/41、状态图。

## PD-034：REL 拒绝必须回退关联 LINK 与 CASE

**决策**：新增 EV-20；主管拒绝 `REL_PENDING_APPROVAL` 时，匹配 LINK 为 0 条只拒绝 REL，为 1/N 条时全部进入 `LINK_FAILED`，受影响 CASE 聚合为 `CASE_FIXING`。
**依据**：全量复检发现人工拒绝 REL 会让 LINK_PENDING_RELEASE 和 CASE_VERIFIED_PENDING_RELEASE 无出口。
**失败处理**：REL/LINK/CASE/AUD 原子提交；任一失败保持待审批和待办，不允许遗留待发布 CASE。
**证据**：PRD G-28、FR-020/024、状态总表 EV-20、AC-G-43。

## PD-035：EV-18 多知识条目的双层幂等键

**决策**：EV-18 保留 `SRC:{src_id}:v{n}:CASE:{case_id}` 作为 CASE 级键，并为每个后继 LINK 使用 `SRC:{src_id}:v{n}:CASE:{case_id}:ITEM:{knowledge_item_id}` 子键。
**依据**：同一来源失效可能为同一 CASE 的多个知识条目各创建或更新一条 LINK，单层 CASE 键无法区分 N 条子链路。
**失败处理**：相同子键返回原 LINK；不同 knowledge_item_id 必须各自处理，不得因 CASE 键重复而漏建。
**证据**：PRD G-23、状态总表 EV-18、AC-G-32/37。

## PD-036：KB 拒绝或撤回必须回退关联 LINK 与 CASE

**决策**：新增 EV-21；KB 业务审核拒绝或撤回时，匹配 LINK 为 0 条只更新 KB，为 1/N 条时全部活动 LINK 进入 `LINK_FAILED`，受影响 CASE 聚合为 `CASE_FIXING`。
**依据**：全量复检发现活动 LINK 会因 KB 终止而永久失去推进对象，并阻塞同知识条目的下一次修复。
**失败处理**：KB/LINK/CASE/AUD 原子提交；失败保持 KB 原状态和修复待办，不产生活动 LINK 卡死。
**证据**：PRD G-29、FR-018/023、状态总表 EV-21、AC-G-45。
