# U1-U9 异常与系统拦截附录

版本：V1.4
日期：2026-10-23  
适用范围：全部 30 条功能需求与 12 条核心任务

## 1. 拦截原则

- 拦截必须阻止动作，而不是只显示警告；
- 安全类错误优先于业务规则争论；
- 无证据、渠道冲突和权限不足均不得生成确定承诺；
- 每个拦截都要产生可审计记录；
- 恢复路径必须明确责任角色和状态。

## 2. U1-U9 详细规则

### U1 安全漏升级

触发：R2/R3 信号出现，或建议仍包含普通排查/退换结论。

系统动作：

- 阻止建议发送；
- 将咨询任务挂起；
- 创建 `ESC_CANDIDATE`；
- 进入安全止损和升级流程；
- 记录命中规则、输入证据和操作人。

恢复：风险单经主管/安全角色关闭，且咨询任务重新评估后才能继续。

验收：

- Given 客户报告“充电盒鼓包且仍在充电”
- When 系统生成普通售后建议或用户要求发送
- Then 必须阻断并创建 `ESC`，不得发送退换/保修结论。

### U2 越权承诺

触发：建议或知识发布包含退款、赔偿、免费换新、免费维修、法律结论或未经授权责任承担。

系统动作：

- 阻断发送/发布；
- 标记为 `REQUIRE_APPROVAL` 或 `BLOCK`；
- 保留原始文本与拦截原因；
- 转售后、主管、业务/渠道或法务。

恢复：授权角色书面确认后生成新的建议或发布候选。

验收：

- Given 知识包含“购买两年直接换新”
- When 提交发布
- Then 必须阻断，要求保障合同、业务批准和评测证据。

### U3 无依据结论

触发：上下文不完整、证据缺失、证据冲突或确定性为 `UNKNOWN/CONFLICT`，但建议为确定语气。

系统动作：

- 改为 `REQUIRE_INPUT` 或 `CONFLICT_HOLD`；
- 展示缺失字段或不确定项；
- 证据缺失、证据冲突或当前角色无权限时转对应人工角色。

恢复：补齐必要上下文/有效证据后重新生成建议。

### U4 错误证据

触发：引用过期、撤回、不可访问、已停用、不在当前发布版本或适用范围不匹配的知识。

系统动作：

- 阻断引用；
- 标记 `EVIDENCE_INVALID`；
- 阻止直接答案和发布；
- 创建或关联问题案例。

恢复：更新来源/知识版本并通过评测与发布审批。

来源失效响应：

| 受影响对象状态 | 唯一目标状态 | 责任角色 |
|---|---|---|
| `KB_BUSINESS_REVIEW`、`KB_EVAL_PENDING`、`KB_APPROVED_FOR_RELEASE` | `KB_SOURCE_BLOCKED` | 知识运营 |
| `EVAL_PLANNED`、`EVAL_RUNNING` | `EVAL_BLOCKED` | AI 评测 |
| `REL_PENDING_APPROVAL` | `REL_REJECTED` | 客服主管 |
| `REL_ACTIVE` | `REL_SUSPENDED` | 客服主管/安全角色 |

历史 KB、EVAL、REL 不改写；修复必须创建新候选并重新完成审核、评测和发布。

### U5 渠道误判

触发：平台、卖家、品牌、授权服务商责任被混为一谈，或渠道事实冲突。

系统动作：

- 将任务/证据标为 `CONFLICT`；
- 暂停责任和承诺判断；
- 转业务/渠道负责人或主管；
- 保留双方证据。

恢复：渠道责任主体被确认，或案例以未决/延期状态继续。

### U6 危险操作

触发：拆机、加热、吹风、穿刺、湿态充电、继续使用危险设备或靠近冒烟设备。

系统动作：

- 立即阻断；
- 替换为安全止损动作；
- 创建/升级 `ESC`；
- 记录原危险内容和拦截结果。

恢复：风险解除且授权角色确认后，才允许继续普通售后。

### U7 遗漏追问

触发：核心任务必需条件未补齐。

系统动作：

- 阻止生成确定性建议；
- 返回缺失字段和追问清单；
- 保留任务为 `CONTEXT_PENDING` 或 `ASSESSING`。

恢复：缺失字段补齐，或主管确认无法取得并以受限状态处理。

### U8 隐私越界

触发：请求密码、验证码、完整支付凭证、与售后无关的身份信息，或在日志/审计中明文保存敏感信息。

系统动作：

- 阻断请求或字段提交；
- 提供最小必要字段替代；
- 脱敏日志；
- 记录隐私拦截事件。

恢复：仅收集足以处理任务的信息；真实隐私策略需法务确认。

### U9 知识不闭环

触发：无原因、无责任角色、无修复或无回归证据；存在活动 LINK；最新 LINK 为 FAILED；或使用无 LINK 例外但缺少双角色批准，却尝试关闭案例或发布。

系统动作：

- 禁止关闭/发布；
- 自动生成后继 LINK、明确弃置或无需知识修复的待办；
- 保留原建议和证据；
- 设置责任角色。

恢复：每个知识条目的最新 LINK 为 RELEASED/ABANDONED 且无活动 LINK；或完成无需知识修复双角色批准。

### KB 冻结与 EVAL 失败

- `KB_DRAFT` 仅在首次提交业务审核前可编辑；
- 提交业务审核后，正文、适用条件和来源引用冻结；
- EVAL 失败时，原 KB 进入只读 `KB_EVAL_FAILED`，不得改回 `KB_DRAFT`；
- EV-09 只创建/重开 `CASE_FIXING` 并写审计，不修改原 KB；
- EV-14 从 `CASE_FIXING` 创建新的 `KB_DRAFT` 版本，旧 KB 保留。

### EV-08 原子发布推进

EV-08 必须同时完成：

1. KB 进入 `KB_APPROVED_FOR_RELEASE`；
2. 0 条匹配 LINK 时跳过 LINK/CASE；1 条或 N 条匹配 LINK 时全部进入 `LINK_PENDING_RELEASE` 并写 `rel_id`；
3. 按每个受影响 CASE 的全部知识条目最新 LINK 重新聚合 CASE；
4. 创建新的 `REL_PENDING_APPROVAL`；
5. 写入 KB/LINK/CASE/REL/AUD 关联审计。

任一步失败时不得提交任何部分结果。有 LINK 时保持原状态，不得留下 REL 已创建但 LINK 或 CASE 未推进的状态。

### CASE_LINK 生命周期与聚合关闭

- `LINK_OPEN`：EV-14 创建 KB_DRAFT 时同时创建；同一 case+knowledge_item 已存在活动 LINK 时拒绝重复开链；
- `LINK_PENDING_RELEASE`：EV-08 评测通过并绑定 REL 候选；
- `LINK_RELEASED`：EV-11 对应 REL 生效；
- `LINK_ABANDONED`：EV-19 经主管与业务/渠道负责人独立批准，记录不发布理由；
- `LINK_FAILED`：EV-09 评测失败或 EV-18 来源失效；不得直接关闭 CASE，必须后继修复或明确弃置；
- `LINK_RELEASED` 和 `LINK_ABANDONED` 不回退；回滚或来源失效只创建新 `LINK_OPEN`；
- 一个 CASE 可按不同 `knowledge_item_id` 并行修复，但同一知识条目同时最多一条活动 LINK；
- CASE 关闭必须无 `LINK_OPEN/LINK_PENDING_RELEASE`，且每个知识条目最新 LINK 为 `LINK_RELEASED/ABANDONED`；
- CASE 无 LINK 时，仅允许“无需知识修复”主管+业务批准，不得用空集合绕过真实修复。

### 风险恢复强制链

1. `ASQ` 因 R2/R3 进入 `ASQ_PAUSED`；
2. `ESC` 记录 `paused_from_state`；
3. `ESC_DISMISSED` 后重新校验 CTX、EVD、ADV；
4. 三者有效时恢复 `paused_from_state`；
5. 原 ADV 失效时必须生成新 ADV 版本或进入 `ASQ_ASSESSING`；
6. 风险关闭但售后问题未解决时，ASQ 进入 `ASQ_ASSESSING`，不得直接关闭。

### 回滚强制链

1. 正常回滚由 EV-12 将 `REL_ACTIVE` 置为 `REL_SUSPENDED`；
2. 来源失效或异常停用后，由 EV-17 从 `REL_SUSPENDED` 创建回滚候选；
3. 历史目标 REL 保持不可变；
4. 复制目标 REL 的 KB 引用生成新的 `REL_PENDING_APPROVAL`；
5. 来源、业务批准、评测和主管确认全部重新校验；
6. 新候选成功进入 `REL_ACTIVE` 后，原故障 REL 进入 `REL_ROLLED_BACK`；
7. EV-13 保留历史 `LINK_RELEASED`，为每个受影响 case+knowledge_item 创建最多一条后继 `LINK_OPEN`，并重开 CASE；
8. 任一步失败时保持 `REL_SUSPENDED` 或 `REL_REJECTED` 及治理待办，不得伪造在线版本或遗漏重开链路。

### EV-18 来源失效进入 CASE 闭环

- EV-04 至 EV-07 完成 KB/EVAL/REL 阻断后，必须触发 EV-18；
- 0 条匹配 LINK/CASE：新建 `CASE_OPEN`，并为其覆盖的每个受影响知识条目创建 LINK_OPEN；
- 活动 LINK：进入 `LINK_FAILED`；
- 已发布 LINK：保持 `LINK_RELEASED`，为受影响路径创建后继 LINK_OPEN；
- 已有未关闭 CASE：进入 `CASE_FIXING`；
- 已关闭 CASE：进入 `CASE_REOPENED`；
- 1 条或 N 条关联：逐个处理全部匹配对象，记录来源版本、受影响 KB/REL 和责任角色；
- CASE 幂等键：`SRC:{src_id}:v{n}:CASE:{case_id}`；
- LINK 子键：`SRC:{src_id}:v{n}:CASE:{case_id}:ITEM:{knowledge_item_id}`；
- EV-18 失败不得回滚已生效的来源阻断，但必须保留治理待办并审计；
- 历史 CASE 证据不可覆盖。

### 风险复发

- `ESC_CLOSED` 与 `ESC_DISMISSED` 是终态；
- 新风险创建新的 `ESC_CANDIDATE`；
- 新 ESC 填写可空 `previous_esc_id` 关联旧单；旧单必须是同客户已关闭或已排除的终态；
- `previous_esc_id` 写入后不可改；自引用、非终态目标和全链循环均拒绝；
- 不允许将旧 ESC 直接改回 `ESC_REOPENED`。

### EV-19 修复链路明确弃置

- 调用角色须取得主管与业务/渠道负责人的独立批准；
- 仅 `LINK_OPEN`、`LINK_PENDING_RELEASE` 或 `LINK_FAILED` 可转为 `LINK_ABANDONED`；
- 记录理由、批准人、证据和审计；
- 弃置后按全部 LINK 重新聚合 CASE，其他知识条目未完成时不得关闭；
- 批准或审计失败时保持原 LINK/CASE 状态并重试，不重复关闭。

### EV-20 REL 拒绝回退

- 主管拒绝 `REL_PENDING_APPROVAL` 时执行 EV-20；
- 匹配 LINK 为 0 条时只拒绝 REL；
- 匹配 LINK 为 1 条或 N 条时，全部进入 `LINK_FAILED`；
- 受影响 CASE 按全部 LINK 重新聚合，并进入 `CASE_FIXING`；
- REL、LINK、CASE、AUD 原子提交；任一失败时 REL 保持待审批并保留审批待办；
- 重复请求使用 `REL:{id}:REJECT_FAIL_LINK` 返回原结果，不重复回退 LINK/CASE。

### EV-21 KB 拒绝或撤回回退

- KB 业务审核拒绝或撤回后触发 EV-21；
- 匹配 LINK 为 0 条时只保留 KB 终态；
- 匹配 LINK 为 1 条或 N 条时，全部 `LINK_OPEN/LINK_PENDING_RELEASE` 进入 `LINK_FAILED`；
- 受影响 CASE 按全部 LINK 聚合，并进入 `CASE_FIXING`；
- KB/LINK/CASE/AUD 原子提交；失败保持 KB 原状态和修复待办，不允许活动 LINK 卡住同一知识条目。

## 3. 强制拦截结果

| 类型 | 系统结果 | 是否允许继续 |
|---|---|---|
| `BLOCK` | 阻止动作并记审计 | 否 |
| `REQUIRE_INPUT` | 要求补证 | 补齐后可继续 |
| `REQUIRE_APPROVAL` | 转授权角色 | 批准后可继续 |
| `SAFETY_ROUTE` | 强制进入风险流程 | 风险关闭后可继续 |
| `CONFLICT_HOLD` | 保留冲突、暂停承诺 | 裁决后可继续 |
| `ROLLBACK` | 停用当前发布并切换目标版本 | 回滚完成后重评 |

## 4. 通用失败兜底

| 失败 | 处理 | 责任人 |
|---|---|---|
| 外部系统超时 | 标记数据不可用，进入补证或人工处理 | 处理角色 |
| 审计写入失败 | 阻断风险关闭、发布和回滚确认 | 系统管理员 + 主管 |
| 证据检索不可用 | 不生成确定建议，创建待处理/案例 | 一线/知识运营 |
| 来源不可访问 | `SRC_UNAVAILABLE`，阻断新发布 | 知识运营 |
| 评测服务不可用 | 保持 `REL_PENDING_APPROVAL` | AI 评测/主管 |
| 回滚目标失效 | 保持 `REL_SUSPENDED`，转人工安全处理 | 主管/安全/管理员 |
| 重复提交 | 幂等返回原对象 | 系统 |
| 并发修改 | 拒绝后到写，提示刷新 | 系统/操作人 |

## 5. 验收判定

- 任一 U1、U2、U6 未拦截即测试失败；
- U3-U5 未进入补证/转交/冲突状态即失败；
- U7 未返回必需字段即失败；
- U8 未阻断或脱敏即失败；
- U9 未生成待办或禁止关闭即失败；
- 拦截产生后如果没有恢复路径或责任人，视为需求缺口。
