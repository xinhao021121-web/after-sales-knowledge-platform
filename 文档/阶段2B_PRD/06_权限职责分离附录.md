## 3. 强制职责分离

### G-01 知识提交与批准

- `author_id != business_approver_id`；
- 若业务负责人参与起草，需由更高层级独立业务负责人批准；
- 服务端在提交和批准两个动作都校验；
- 无独立批准人时，知识版本保持业务审核状态，不得进入评测。

### G-02 风险关闭

- R2：必须由客服主管确认关闭；
- R3：必须由法务/安全责任人确认关闭；
- 一线客服和知识运营不能关闭 R2/R3；
- AI 评测和系统管理员不能改变风险等级；
- 风险关闭与咨询任务关闭是两次独立动作。

### G-03 AI 评测与业务批准

- AI 评测通过只证明质量证据存在；
- 业务批准决定政策口径；
- 客服主管确认发布准备；
- 管理员只执行技术动作；
- 任一角色缺失时发布保持待批准。

### G-04 发布与执行

- 发布必须同时有业务批准和评测通过；
- 管理员不能是知识提交人或业务批准人；
- 发布后的停用可由主管或安全责任人发起；
- 回滚目标必须经过复验，否则保持停用。
- `LINK_ABANDONED` 必须由客服主管和业务/渠道负责人独立批准，知识运营执行并记录理由；
- 关闭 CASE 时服务端必须校验 CASE_LINK 聚合，不能把“关闭 CASE”本身当作弃置 LINK 的替代动作。

### G-05 角色委托范围

首版 P0 不支持角色委托或代理审批。需要代班时，由组织管理员在身份系统中变更实际角色，并按新角色重新核验职责分离。

角色委托列入 P1，后续必须单独增加需求、有效期、撤销、冲突校验和验收，不得作为本 PRD 的隐含规则实现。

### G-06 上下文编辑

- 客服主管对 `CTX` 只有读取权限；
- 一线客服和售后专员可创建新的 `CTX` 版本；
- 任何新版本都不得覆盖历史快照；
- 服务端必须拒绝客服主管通过其他入口编辑上下文。

## 4. 责任空位

| 缺失角色 | 系统行为 |
|---|---|
| 无业务/渠道负责人 | 知识版本保持业务审核，不得评测和发布 |
| 无 AI 评测人员 | 候选版本保持评测待执行，不得发布 |
| 无客服主管 | REL 保持待批准；R2 风险无法关闭 |
| 无法务/安全责任人 | R3 保持已升级，不能关闭 |
| 无知识运营 | 可创建 CASE，但修复和发布流程保持待处理 |
| 无业务/渠道负责人 | CASE_LINK 不得弃置；CASE 只能保持修复或待发布，不能以无 LINK 例外关闭 |
| 管理员不可用 | 业务流程可继续，但技术停用/恢复保持待处理并报警 |

任何空位都不得通过普通角色“临时放行”绕过。
