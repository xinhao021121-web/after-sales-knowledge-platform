风险等级怎么理解？

阻断表示知识发布或安全重开无法得到唯一结果。 当前主体规则明确，但对象基数和事件覆盖仍不足。

阻断

核心发布链路无法唯一实现，可能误删有效知识、阻断首次发布或丢失问题闭环。

高风险

异常状态无法合法恢复，可能导致安全记录不可重开或历史记录混淆。

中风险

边界未定，可能造成返工或人工兜底。

低风险

局部文档一致性问题，不影响主流程唯一性。

问题详情

PRD-001 REL 是知识快照还是单条知识发布，尚未唯一确定

阻断对象基数确定缺口
位置与证据
PRD 10 将 REL 的关键字段定义为“KB 集合”；G-17 要求同一租户、环境、业务域仅有一个 REL_ACTIVE。但 EV-08 由一次 EVAL_PASSED 创建新的 REL_PENDING_APPROVAL，且每个 EVAL 只对应一个 KB 候选。
漏洞说明
如果 REL 是业务域快照，研发必须先把当前 ACTIVE REL 的其他 KB 集合复制到新候选；当前事件没有这一步，更新一个知识可能让其他有效知识消失。如果 REL 只对应一个 KB，则“KB 集合”和“业务域唯一 ACTIVE”又会阻止同域多个知识同时在线。
触发场景
REL-A 在线并包含 KB-1、KB-2 → KB-1 新版本 EVAL 通过 → EV-08 创建 REL-B → 若 REL-B 只装 KB-1 新版本 → 激活后 KB-2 失去在线版本。
影响范围
知识检索、REL 组成、发布替代、回滚、关联 CASE、唯一 ACTIVE、审计和所有知识任务。
待确认问题
P0 的一次 REL 是一个业务域快照，还是只对应一个知识条目？
最小修改建议
若采用快照：引入发布候选组成事件，EVAL 通过只把 KB 加入候选；候选从当前 ACTIVE REL 复制其余 KB，再统一审批和激活。若采用单 KB 发布：将 REL 的“KB 集合”改为单一 KB 版本，并把唯一性作用域改为对应知识条目。
关联修改
PRD 10、G-16/G-17、FR-019/020/021、EV-08/EV-11/EV-13/EV-16/EV-17、AC-G-17 至 AC-G-27、追踪矩阵和状态图。

PRD-002 CASE 关联被强制且来源失效未产生 CASE 事件

阻断闭环断裂确定缺口
位置与证据
EV-08 的前置条件明确要求“关联 CASE 存在”，但 FR-017/018/019 允许从知识草稿直接进入审核、评测和发布，没有说明必须先生成 CASE。PRD 11.2 又声明来源失效最终应“CASE 重开或新建”，但 EV-04 至 EV-07 只更新 KB、EVAL、REL，没有目标 CASE 的事件。
漏洞说明
研发无法实现首次知识发布，因为可能没有 CASE；也无法实现来源失效后的知识治理闭环，因为案例状态不会自动恢复或创建。若强行创建 CASE，则每次正常知识发布都会产生一个虚假“问题案例”。
触发场景
新知识从草稿进入审核并通过 EVAL → 没有关联 CASE → EV-08 前置条件失败 → 无法发布；另一场景：在线 SRC 被撤回 → REL 被停用 → 没有事件重开关联 CASE → 问题治理清单遗漏。
影响范围
首次知识发布、正常版本更新、来源失效、CASE 生命周期、发布证据和 U9。
待确认问题
正常知识发布是否允许没有 CASE？一个 REL 或 KB 是否可能关联多个 CASE？
最小修改建议
将 CASE 定义为可选 0..N：有 CASE 时 EV-08 推进全部关联 CASE，无 CASE 时仍可创建 REL。另新增来源失效到 CASE 的事件：已关联 CASE 进入 `CASE_REOPENED` 或 `CASE_FIXING`，无 CASE 时按规则创建治理案例。
关联修改
PRD 10、FR-019/020/024、G-09、11.2、EV-04 至 EV-08、新增事件、AC-G-24/27、AC-K4-02、追踪矩阵。

PRD-003 已关闭或已排除的 ESC 无法重新打开

高风险状态不可达确定冲突
位置与证据
ESC 状态说明中，`ESC_CLOSED` 和 `ESC_DISMISSED` 的失败/回滚路径都写了“新风险重开”，但两者的“下一自身状态”仍是终态或恢复 ASQ；从这两个状态到 `ESC_REOPENED` 没有转换，`ESC_REOPENED` 仅能从 `ESC_MONITORING` 到达。
漏洞说明
研发按状态表实现时，已关闭或已排除的风险出现新证据后无法重开；若直接新建 ESC，又与文档中“重开”的语义不一致。
触发场景
风险单 ESC-01 已关闭 → 客户报告同型号冒烟 → 系统按文字应重开 ESC-01 → 状态表不允许 CLOSED/ DISMISSED 到 REOPENED → 只能绕过或卡死。
影响范围
安全风险复发、责任追溯、客户历史、案例关联和 U1。
待确认问题
复发风险应重开原风险单，还是创建新的风险单并关联旧单？
最小修改建议
建议复发创建新 ESC，并保留 `previous_esc_id` 关联；若要求重开原单，则在 ESC_CLOSED 和 ESC_DISMISSED 增加合法到 ESC_REOPENED 的转换、权限和验收。
关联修改
ESC 对象字段、03 第 1.2 节、FR-013/014、AC-G-10、风险状态图。

PRD-004 V1.2 仍有少量版本记录和事件前缀不一致

低风险文档一致性表达问题
位置与证据
PRD 顶部的版本表包含 V1.2.0，但第十六章变更记录只列 V1.0.0 和 V1.1.0；V1.2 状态表中 `ESC_DISMISSED` 仍引用 `E-02`，其余事件使用 `EV-` 前缀。
漏洞说明
不影响业务规则，但版本追溯和自动引用检查无法保持一致。
触发场景
评审者按第十六章确认 V1.2 变更时找不到记录；自动搜索 EV-02 时遗漏一次引用。
影响范围
PRD 版本审计、文档检索和复检报告。
待确认问题
无；应统一为 V1.2.0 和 EV-02。
最小修改建议
补齐 V1.2.0 变更记录，统一事件前缀，并重新执行文档引用检查。
关联修改
PRD 第十六章、03 第 1.2 节、复检报告和验收记录。

发现问题后，产品经理怎么处理

  1. 先由产品负责人确定发布版本是业务域快照还是单知识条目。
  2. 再明确 CASE 的 0..N 关系，补齐首次发布和来源失效的事件。
  3. 最后修复风险重开和文档一致性，重新执行全量逻辑检查。
