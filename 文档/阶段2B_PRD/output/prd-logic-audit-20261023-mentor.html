风险等级怎么理解？

“阻断”表示核心规则没有唯一实现方式，不代表产品方向错误。 当前状态表把不同对象的状态写入同一“下一状态”字段，研发无法据此稳定实现状态更新。

阻断

核心实现无法唯一，可能造成状态卡死、重复对象或错误恢复。评审前必须关闭。

高风险

主流程可做，但可能造成错误引用、越权编辑或无法回滚，应在开发前明确。

中风险

边界未唯一，较可能造成返工或验收分歧。

低风险

局部表达或可维护性问题，不影响主流程。

PRD-001 跨对象状态所有权被混写

“下一状态”同时容纳本对象状态和其他对象的创建/状态变化，无法唯一确定谁应更新、何时更新及失败时哪个对象回退。

评审放行条件

先区分本对象状态转换与跨对象事件影响，并补齐来源、回滚和角色编辑的唯一定义；完成后重新核对状态表、追踪矩阵、GTW、权限和验收记录。

PRD-001 跨对象状态混写在“下一状态”字段中

阻断状态机断裂确定冲突
位置与证据
《03_状态转换总表》声称对象状态所有权严格分离，但 ASQ_NEW 的下一状态包含 ESC_CANDIDATE，ESC_DISMISSED 返回 ASQ_ASSESSING，KB_EVAL_PENDING 可进入 CASE_OPEN，EVAL_PASSED 可进入 REL_PENDING_APPROVAL，EVAL_FAILED 可进入 CASE_FIXING。
漏洞说明
研发按表实现时，同一行的“下一状态”既可能表示当前对象自身变化，也可能表示创建另一个对象。不同工程师会得到不同实现：有人把 EVAL 改成 REL 状态，有人只在 EVAL 保持 PASSED 并创建 REL，最终造成状态覆盖、重复记录或追踪矩阵无法校验。
触发场景
评测通过 → 系统读取“下一状态 REL_PENDING_APPROVAL” → 一方更新 EVAL 状态，另一方创建 REL → 两个对象状态和审计记录发生分叉。
影响范围
ASQ、ESC、KB、CASE、EVAL、REL、状态实现、事件设计、审计、追踪矩阵和 GTW。
待确认问题
每个状态表是否应拆成“本对象下一状态”和“跨对象事件/创建动作”两列？
最小修改建议
统一规定：当前对象只能进入自己的状态；“创建 ESC/CASE/REL”和“使父对象暂停/恢复”写入独立事件列。跨对象影响必须指明来源对象、目标对象、触发事件和幂等规则。
关联修改
03 全部跨对象行；02 需求追踪矩阵的 state_transition；04 GTW 中状态断言；07 PRD 决策记录；08 阶段验收记录。

PRD-002 来源首次登记与失效传播缺少完整状态路径

高风险条件缺失确定缺口
位置与证据
FR-015 要求创建来源并标记核验状态，FR-016 要求来源变化触发 KB 影响评估；但《03_状态转换总表》的 SRC 从 SRC_ACTIVE 开始，没有首次登记/待核验状态。KB 的 KB_EVAL_PENDING 和 REL 的 REL_PENDING_APPROVAL 也没有在来源突然失效时被阻断的明确转换。
漏洞说明
研发可能把新建来源直接设为 ACTIVE，或只更新 SRC、不更新依赖它的 KB/REL。这样来源已失效但评测或发布仍可继续，违反 PRD 的 G-04 和 U4。
触发场景
KB 处于评测待执行 → SRC 被撤回 → 系统只把 SRC 改为 WITHDRAWN → EVAL 继续通过 → REL 仍可发布错误知识。
影响范围
来源登记、知识审核、评测、发布、回滚、证据引用、审计和发布影响评估。
待确认问题
新来源的初始状态是否固定为待核验，以及来源失效时应自动阻断哪些 KB/EVAL/REL 状态？
最小修改建议
增加 SRC_REGISTERED 或等价初始态；ACTIVE 必须同时满足可访问、标题、范围、有效期和责任人校验。来源撤回/过期/不可访问时，向 KB、EVAL、REL 发出阻断事件，并写明各对象的回退状态。
关联修改
FR-015、FR-016、FR-019、FR-020、G-04、AC-G-11、03 第 4/5/7/8 节、02 矩阵对应行。

PRD-003 回滚后如何恢复旧版本没有唯一实现

高风险恢复路径确定缺口
位置与证据
FR-021 要求选择已验证的回滚目标；状态表把 REL_SUPERSEDED 和 REL_ROLLED_BACK 定义为终态，同时提示“重新启用需新审批”，但没有定义如何生成新的待批准 REL，也没有写明回滚目标必须是 ACTIVE、SUPERSEDED 还是可复制版本。
漏洞说明
研发可能直接修改旧 REL 为 ACTIVE，破坏不可变与审批；也可能把旧 REL 保持终态，导致系统回滚完成后没有任何在线版本。
触发场景
REL-B 出现严重错误 → 主管选择 REL-A 为回滚目标 → 系统把 REL-B 标为 ROLLED_BACK → REL-A 仍是 SUPERSEDED 终态 → 新建议没有有效发布版本。
影响范围
线上知识可用性、回滚事务、业务审批、案例重开、审计和所有检索请求。
待确认问题
回滚是直接激活历史 REL，还是复制历史内容生成新的 REL 并重新审批？
最小修改建议
建议保持历史 REL 不可变，回滚时创建新的发布候选并继承历史版本引用；或明确增加受控的 REL_REACTIVATION_PENDING，但必须重新审批和审计。同时明确“唯一 ACTIVE”是全局还是按租户/环境/业务域。
关联修改
FR-020、FR-021、AC-G-15、03 REL 状态机、10 发布对象字段、13.2 发布门槛、权限附录“停用/回滚”。

PRD-004 客户上下文编辑角色与权限矩阵冲突

高风险权限冲突确定冲突
位置与证据
FR-004 用户故事写“作为售后/主管，我希望修正错误上下文”，正常流程也允许该用户创建新版本。06 权限矩阵中，编辑 CTX 只有一线客服、售后专员为“执行”，客服主管仅为“读取”。
漏洞说明
若研发按 FR-004 开放主管编辑，权限测试会失败；若按权限矩阵关闭，主管无法执行需求中描述的动作。页面、接口和审计无法形成一致实现。
触发场景
客服主管点击“修正上下文” → FR-004 允许 → 服务端按权限附录拒绝 → 需求验收出现争议。
影响范围
上下文的准确性、主管纠错、权限服务端校验、审计和 FR-004/AC-G-04。
待确认问题
主管是否应拥有上下文编辑权，还是只能通过售后/一线提交修正？
最小修改建议
二选一并统一全文；若选择主管可编辑，则更新 06 矩阵和权限测试；若选择只读，则修改 FR-004 用户故事与流程。
关联修改
PRD 3.1、7.1 FR-004、06 权限矩阵、AC-G-04、02 矩阵 FR-004 行、阶段 2B 验收记录。

PRD-005 风险排除后的咨询恢复状态不明确

中风险回退路径表达问题
位置与证据
ESC_DISMISSED 的下一状态写为“返回 ASQ_ASSESSING”，但风险可能从 ASQ_NEW、ASQ_CONTEXT_PENDING、ASQ_ADVICE_PENDING、ASQ_HANDOFF_PENDING 或 ASQ_RESPONDED 触发。
漏洞说明
统一回到 ASSESSING 可能跳过上下文补齐、丢弃待确认建议或破坏已有转交。研发无法判断应恢复原状态还是重新评估。
触发场景
建议已待确认 → 客服标记疑似风险 → 风险排除 → 系统强制回到 ASSESSING → 原先的待确认建议失效，但 PRD 未说明是否重新生成、是否保留。
影响范围
ASQ 状态、ADV 版本、上下文的继续使用、转交待办和客户沟通连续性。
待确认问题
风险排除后应恢复到进入风险前的 ASQ 状态，还是统一重新判断？
最小修改建议
ESC 记录 paused_from_state；排除后恢复该状态，并重新校验 CTX/EVD/ADV。若原 ADV 失效，明确生成新版本或回到 ASSESSING。
关联修改
ESC 对象字段、FR-013、03 ASQ/ESC 状态机、AC-S1-S4、审计字段。

PRD-006 角色委托规则没有进入功能需求与验收

中风险权限遗漏确定缺口
位置与证据
权限附录 G-05 定义了有时限、可审计的角色委托，并禁止委托给同一提交人自批或管理员批准业务；但 FR-026/FR-027、AC-G-01/AC-G-04 和追踪矩阵没有委托对象的创建、撤销、生效时间、冲突和审计验收。
漏洞说明
研发可能忽略委托，导致真实请假场景无法办理；也可能实现成永久权限，绕过职责分离。
触发场景
业务负责人委托他人批准知识 → 系统未校验委托有效期或不可委托边界 → 同一知识提交人被委托批准 → 发生自审自批。
影响范围
角色权限、职责分离、审批、发布、审计和异常处理。
待确认问题
首版是否提供角色委托，还是仅记录线下授权并通过新成员角色处理？
最小修改建议
若首版支持，增加委托功能、有效期、范围、撤销和验收；若不支持，从权限附录移除或标明后续范围。
关联修改
06 G-05、FR-026/FR-027、AC-G-01/AC-G-04、02 追踪矩阵、08 验收记录。

发现问题后，产品经理怎么处理

  1. 先统一状态机表达，再修改来源与回滚规则，避免继续在错误模型上补需求。
  2. 由项目负责人明确 CTX 编辑权限和角色委托是否进入首版。
  3. 拍板后同步修改 PRD、追踪矩阵、GTW、权限附录、状态表、图表说明和验收记录。
