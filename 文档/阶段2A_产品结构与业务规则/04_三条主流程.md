# 三条端到端主流程

版本：V0.1  
日期：2026-10-22

## 1. 通用前置规则

所有流程在创建售后咨询任务后，立即执行风险识别：

- R0/R1：进入常规规则判断流程；
- R2/R3：进入高风险流程；
- 在常规流程中任何时候发现 R2/R3，立即暂停建议生成并转入高风险流程；
- 风险流程未解除前，不得继续以普通知识回答退换、保修或费用问题。

## 2. 流程一：常规售后规则判断

### 2.1 流程目标

适用于 R0/R1 场景，使一线在不越权承诺的前提下获得基于有效证据的条件性建议。

### 2.2 端到端步骤

| 步骤 | 负责人 | 输入 | 处理 | 输出/门禁 |
|---|---|---|---|---|
| 1. 建立咨询任务 | 一线客服/售后专员 | 客户原始诉求 | 创建 `ASQ`，规范化诉求，记录初始风险 | 任务建立 |
| 2. 补齐客户上下文 | 一线客服/售后专员 | 商品、渠道、时间、状态 | 创建 `CTX`，识别缺失字段，向客户追问 | 上下文达到可判断条件 |
| 3. 检索有效证据 | 系统生成，客服核验 | `CTX`、已发布 `REL/KB` | 检索适用知识，保留条件、例外和来源 | `EVD` 至少一条有效，或进入知识缺口 |
| 4. 条件判断 | 客服/售后 | `CTX + EVD` | 判断规则是否适用；识别冲突和不确定性 | `ADV` 为条件性建议 |
| 5. 生成建议 | 系统生成，人确认 | 判断结果 | 输出动作序列、追问、证据、承诺边界 | 建议状态为待人工确认 |
| 6. 风险复核 | 系统强制 + 客服 | `ADV` | 再次检查安全、越权和危险操作 | 有风险则转流程二 |
| 7. 人工确认 | 一线客服/售后 | `ADV`、证据 | 确认、修改或驳回；必要时转售后/主管 | 建议被采用或转手 |
| 8. 对客处理 | 一线客服/售后 | 已采用建议 | 答复、补证、安排检测或渠道沟通 | 客户实际下一步 |
| 9. 结果记录 | 一线客服 | 客户反馈/处理记录 | 标记已解决、待客户、转交或重开 | `ASQ` 状态推进 |
| 10. 问题沉淀 | 客服/知识运营 | 失败或缺口 | 创建 `CASE`，保留原建议和证据 | 进入流程三 |

### 2.3 判断门禁

- 关键条件缺失时只能给补证或安全通用动作，不能给确定结论；
- 证据必须指向已发布知识版本；
- 发现渠道冲突时停止承诺并转渠道负责人；
- 建议必须由人工确认后才能发送；
- 只有“客户实际完成下一步且结果可记录”才能视为解决，不以已答复代替已解决。

### 2.4 关键对象链

`ASQ -> CTX -> EVD -> ADV -> AUD`

发现缺口后增加：

`ASQ/ADV -> CASE -> EVAL/REL`

## 3. 流程二：高风险售后

### 3.1 流程目标

在冒烟、明火、明显过热、鼓包、进液后异常、人身不适或渠道身份高风险时，先保护人身和设备安全，再进行有限诊断与责任处理。

### 3.2 端到端步骤

| 步骤 | 负责人 | 输入 | 处理 | 输出/门禁 |
|---|---|---|---|---|
| 1. 识别风险 | 任意角色/系统提示 | 客户描述、照片、上下文 | 标记 R2/R3 和风险信号 | 创建 `ESC` 候选 |
| 2. 暂停普通流程 | 系统强制 | 当前 `ASQ/ADV` | 停止普通建议发送和费用/退换争议 | 普通流程进入暂停态 |
| 3. 立即止损 | 一线客服/售后 | 风险信号 | 停止使用/充电、远离可燃物、禁止拆机或危险操作 | 客户收到止损动作 |
| 4. 必要追问 | 一线客服 | 风险信号 | 只问是否冒烟/明火/受伤/异味/鼓包/位置 | 信息足够升级 |
| 5. 风险确认 | 客服主管；R3 安全/法务 | `ESC` | 确认风险等级，判断是否紧急处置 | `ESC` 进入已升级 |
| 6. 转交处理 | 客服主管/售后/安全角色 | 事件信息 | 转售后检测、安全支持或必要应急渠道 | 责任角色明确 |
| 7. 观察与记录 | 责任角色 | 客户后续、服务记录 | 记录处置、伤害、证据和未决事项 | `ESC` 进入观察/待关闭 |
| 8. 关闭或重开 | 安全责任角色 | 关闭证据 | R2 由主管批准，R3 由安全/法务批准；异常则重开 | `ESC` 关闭/重开 |
| 9. 知识和流程复盘 | 知识运营/主管 | `ESC/CASE` | 判断是否需新增安全知识或流程变更 | 进入流程三 |

### 3.3 强制安全门禁

- 风险流程创建后，普通客服流程不得继续向客户提供退换修结论；
- R3 未获安全/法务角色确认不得关闭；
- 任何角色不得把“继续充电”“拆机检查”等危险动作作为排查建议；
- 客户争议或渠道责任不能降低风险等级；
- 关闭风险单前必须有止损、转交和后续记录。

### 3.4 关键对象链

`ASQ -> ESC -> CTX(补充) -> ESC -> CASE`

必要时保留被暂停的 `ADV`，用于审计，但不得作为有效对客建议。

## 4. 流程三：知识问题闭环

### 4.1 流程目标

把客服纠错、知识缺口、证据冲突、风险和评测失败转化为可追踪的知识修复与回归过程。

### 4.2 端到端步骤

| 步骤 | 负责人 | 输入 | 处理 | 输出/门禁 |
|---|---|---|---|---|
| 1. 发现问题 | 客服/售后/主管/评测 | 失败建议、重复联系、风险事件、冲突证据 | 创建 `CASE`，保留原咨询、建议、证据和版本 | 案例待分诊 |
| 2. 分诊 | 知识运营 | `CASE` | 判断是知识、规则、渠道、检索、表达、安全或流程问题 | 问题类型明确 |
| 3. 保留证据 | 知识运营/客服 | 原始材料、链接、服务记录 | 固定来源和上下文，禁止覆盖 | 证据状态完整 |
| 4. 分析原因 | 知识运营 + 业务/渠道 | `CASE` | 识别缺失、过期、冲突或适用范围错误 | 责任角色和修复方案 |
| 5. 修复知识 | 知识运营 | 修复方案和有效来源 | 新建知识版本 `KB`，不得覆盖历史版本 | 草稿待审核 |
| 6. 复核来源状态 | 知识运营 | `SRC` 与引用关系 | 确认来源为 `SRC_ACTIVE`；失效来源触发知识复核 | 来源门禁通过/阻断 |
| 7. 业务审核 | 业务/渠道负责人 | `KB + SRC` | 确认事实、适用条件和承担责任 | `KB` 可进入评测 |
| 8. 回归评测 | AI 评测 | `KB + EVAL + 冻结核心任务` | 验证核心任务、风险和不可接受错误 | `EVAL_PASSED/FAILED/BLOCKED` |
| 9. 发布准备 | 客服主管 | 业务批准 + 评测通过 | 确认发布范围、回滚目标和运行准备 | `REL_PENDING_APPROVAL` |
| 10. 发布或停留待发布 | 知识运营执行；主管确认 | `REL_PENDING_APPROVAL` | 发布后 `REL_ACTIVE`；不发布需联合决定并留证 | 案例关闭/待发布 |
| 11. 关闭/回滚 | 知识运营/主管/评测 | 发布结果 | 生效后关闭案例；异常则回滚并重开案例 | `CASE/REL` 完成闭环 |

### 4.3 强制门禁

- 案例证据和原建议不可被新知识覆盖；
- 知识提交人不得批准自己的知识；
- 知识来源不是 `SRC_ACTIVE` 时，不得进入新发布；
- 业务负责人未批准，不得发布政策相关版本；
- AI 评测未通过，不得进入发布；
- AI 评测通过不能替代业务批准；
- 管理员不能直接跳过审批和评测；
- 案例在 `CASE_VERIFIED_PENDING_RELEASE` 时不得直接关闭；
- 发布版本 `REL_ACTIVE` 生效后才可确认案例发布完成；
- 发布后发现问题必须停用/回滚并创建或重开案例。

### 4.4 关键对象链

`ASQ/ESC/ADV -> CASE -> KB/SRC -> EVAL -> REL -> AUD`

中间状态：

`CASE_EVIDENCE_READY -> CASE_FIXING -> CASE_REGRESSION_PENDING -> CASE_VERIFIED_PENDING_RELEASE -> REL_ACTIVE -> CASE_CLOSED`

失败路径：

`EVAL 失败 -> CASE 重开 -> 修复 KB -> 新 EVAL`

来源失效：

`SRC_EXPIRED/WITHDRAWN -> 关联 KB 复核 -> REL 影响评估 -> 停用/回滚或新版本`

发布后异常：

`REL 回滚 -> CASE 重开 -> 新 KB/EVAL`

## 5. 三条流程的共同规则

1. 一次客户输出必须关联任务、上下文版本、建议版本和证据；
2. 普通答复不得绕过风险识别；
3. 知识发布不得跳过业务审核和评测；
4. 任何关键动作必须产生审计记录；
5. 未完成的事项必须保留为待办、升级或案例，不能默认为解决。
