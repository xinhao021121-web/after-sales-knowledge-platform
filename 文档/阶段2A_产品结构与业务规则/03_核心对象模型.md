# 核心业务对象模型

版本：V0.1  
日期：2026-10-22  
说明：这是产品概念模型，不是数据库表设计

## 1. 对象总览

| 对象 | 唯一标识 | 核心职责 | 主要责任人 | 关键状态 |
|---|---|---|---|---|
| 售后咨询任务 | `ASQ-{日期}-{序号}` | 承载一次客户售后诉求及其处理过程 | 一线客服 | 新建、待补证、判断中、建议待确认、已答复、已转交、已解决、已关闭 |
| 客户上下文 | `CTX-{咨询ID}-{版本}` | 记录一次判断所依据的商品、渠道、时间、状态与客户诉求 | 一线客服/售后专员 | 快照有效、需补证、冲突、作废 |
| 知识来源 | `SRC-{来源类型}-{编号}-v{版本}` | 记录官方资料或业务规则的原始出处、适用范围和有效期 | 知识运营 | 活跃、待复核、已过期、已替代、已撤回、不可访问 |
| 知识条目版本 | `KB-{业务域}-{序号}-v{版本}` | 将来源转化为可审阅的业务口径 | 知识运营提交；业务负责人批准 | 草稿、业务审核、评测待执行、可发布、已拒绝、已撤回 |
| 检索证据 | `EVD-{咨询ID}-{序号}` | 建立建议与知识版本、来源和适用范围之间的证据关系 | 系统生成，客服核验 | 有效、不适用、冲突、缺失 |
| 处理建议 | `ADV-{咨询ID}-{版本}` | 给出条件、动作、证据和承诺边界 | 一线客服/售后专员确认 | 草稿、待确认、已采用、已驳回、已失效 |
| 风险升级单 | `ESC-{咨询ID}-{序号}` | 记录 R2/R3 风险、已采取措施、升级对象和结果 | 触发角色发起；安全责任链路关闭 | 候选、确认、止损中、已升级、观察中、已关闭、已重开 |
| 问题案例 | `CASE-{来源}-{序号}` | 承载知识缺口、错误建议、渠道冲突或重复问题 | 知识运营 | 待分诊、证据中、修复中、待回归、评测通过待发布、已关闭、已重开、已延期 |
| 评测任务 | `EVAL-{发布候选}-{序号}` | 用冻结核心任务验证知识、规则或发布候选 | AI 评测人员 | 待执行、执行中、通过、失败、受阻 |
| 发布版本 | `REL-{业务域}-{日期}-{序号}` | 固化一次可回滚的知识与规则集合，并唯一表示对外生效状态 | 客服主管批准；知识运营执行 | 待批准、已拒绝、已发布、已替代、已停用、已回滚 |
| 审计记录 | `AUD-{对象类型}-{序号}` | 记录关键读取、判断、审批、发布和异常操作 | 系统生成；管理员维护机制 | 已记录（不可变） |

## 2. 对象定义

### 2.1 售后咨询任务 `ASQ`

承载客户的一次售后诉求，是主流程的入口。

业务内容：

- 客户原始诉求与规范化诉求；
- 当前主要验证域；
- 当前风险等级和确定性状态；
- 当前上下文快照；
- 负责角色和处理状态；
- 关联建议、升级、案例和审计记录。

一个咨询任务可以有多个上下文版本和建议版本，但任何一次对客户输出都必须对应明确的版本。

### 2.2 客户上下文 `CTX`

代表“在处理该问题时已知和未知的事实”。

业务内容：

- 商品身份：品牌、型号、序列号/识别信息；
- 渠道：销售主体、履约主体、服务入口；
- 时间：购买、签收、服务、当前时间关系；
- 商品状态：完好、损坏、进液、变形、配件；
- 客户诉求与故障表现；
- 已知证据、缺失字段、冲突标记；
- 上下文完整度 C0-C3。

上下文是版本化快照。后续补充信息不能覆盖原记录，必须产生新版本并保留差异。

### 2.3 知识来源 `SRC`

代表知识的原始依据，不等同于知识条目。

业务内容：

- 来源类型：法规、官方政策、操作指南、安全说明、渠道规则、内部 SOP；
- 原始 URL 或本地证据；
- 标题、访问/核验日期；
- 发布组织；
- 适用范围和有效期；
- 来源状态和替代关系。

来源状态由知识运营维护，状态转换如下：

| 当前状态 | 触发人 | 触发条件 | 允许动作 | 下一状态 | 失败/回滚 |
|---|---|---|---|---|---|
| 活跃 `ACTIVE` | 知识运营 | 来源可访问、日期有效、范围明确 | 被知识版本引用 | 待复核 / 已过期 / 已替代 / 已撤回 / 不可访问 | 无法核验则进入待复核 |
| 待复核 `REVIEW_REQUIRED` | 知识运营/规则变更事件 | 到期临近、来源变化或引用冲突 | 复核原文、更新范围或替换来源 | 活跃 / 已过期 / 已撤回 / 不可访问 | 复核失败保持待复核并阻断新发布 |
| 已过期 `EXPIRED` | 知识运营/系统到期事件 | 超过有效期或规则失效 | 停止新引用、创建新来源版本 | 已替代 / 已撤回 | 不能直接恢复活跃；须重新登记有效版本 |
| 已替代 `SUPERSEDED` | 知识运营 | 新来源版本已批准 | 保留历史、被引用知识进入待复核 | 终态 | 新版本回滚时只能将旧版本标为待复核，不能自动恢复活跃 |
| 已撤回 `WITHDRAWN` | 来源发布方/法务/业务负责人发起，知识运营登记 | 官方撤回、法律变化或无效声明 | 立即阻断新发布，关联知识进入待复核/停用评估 | 终态 | 不得自行恢复；需重新取证并走新版本流程 |
| 不可访问 `UNAVAILABLE` | 知识运营/系统检测 | URL、文件或工单无法访问 | 保留最后核验信息，禁止新发布引用 | 待复核 / 已撤回 | 恢复访问后仍需复核，不自动转为活跃 |

来源失效不会直接改写已发布知识状态，而是触发关联知识版本进入 `REVIEW_REQUIRED`，并由客服主管和 AI 评测人员评估是否停用或回滚发布版本。

### 2.4 知识条目版本 `KB`

代表经过整理、可被引用和评测的业务知识。

业务内容：

- 事实主张与允许动作；
- 适用商品、渠道、地区、时间和风险条件；
- 例外与禁止事项；
- 引用来源版本；
- 业务负责人和批准记录；
- 知识与来源的版本关系；
- 生效、失效、替代和回滚状态。

知识条目版本只拥有“内容是否经过业务批准和评测、是否可供发布”的状态，不拥有对外生效状态。知识版本一旦进入可发布状态不可原地修改，只能创建新版本。

对外是否生效只由 `REL` 发布版本决定。一个知识版本可以出现在多个发布版本中，因此其“当前是否在线”是从有效的 `REL` 关系派生，而不是知识版本自身的独立状态。

### 2.5 检索证据 `EVD`

关联一次咨询与具体知识版本，回答“为什么这条建议有依据”。

业务内容：

- 命中的知识条目版本；
- 匹配的适用条件与未满足条件；
- 来源及版本；
- 证据摘要；
- 证据有效性判断；
- 是否存在冲突或过期风险。

证据不是知识副本，也不能脱离知识版本和来源单独存在。

### 2.6 处理建议 `ADV`

面向客服和售后专员的受约束处理建议。

业务内容：

- 对诉求的理解；
- 已满足和未满足条件；
- 标准动作序列；
- 需要追问的字段；
- 必须转交的角色；
- 引用证据集合；
- 承诺边界和禁止动作；
- 人工确认结果。

建议不直接等于客户答复，必须由有权限的人确认后发送。

### 2.7 风险升级单 `ESC`

当咨询出现 R2/R3 风险时，承载独立的安全处理链。

业务内容：

- 风险信号；
- 已执行的止损动作；
- 尚未确认的风险信号；
- 触发角色和升级对象；
- 客户沟通记录；
- 安全/法务确认；
- 关闭或重开理由。

R2/R3 状态独立于咨询任务，不能因为咨询被“已答复”而自动关闭。

### 2.8 问题案例 `CASE`

连接一线问题和知识维护的载体。

业务内容：

- 来源：客服纠错、客户重复联系、风险升级、评测失败、渠道冲突；
- 原始问题、建议和证据；
- 问题类型与根因；
- 责任角色；
- 修复动作；
- 回归任务和结果；
- 关闭或重开原因。

评测通过但尚未发布时，案例合法停留于 `CASE_VERIFIED_PENDING_RELEASE`。该状态不能直接关闭；只有发布版本进入 `REL_ACTIVE`，或客服主管与业务/渠道负责人明确作出“不发布”决定并记录理由，才能关闭。

### 2.9 评测任务 `EVAL`

对知识版本、规则变更或发布候选进行受控验证。

业务内容：

- 评测对象与版本；
- 引用的冻结核心任务；
- 预期动作和不可接受错误；
- 实际结果；
- 失败分类；
- 评测人员、时间和结论。

### 2.10 发布版本 `REL`

把一组已批准且已验证的知识版本固定为可引用版本。发布版本是“当前对外生效状态”的唯一所有者。

业务内容：

- 包含的知识版本；
- 业务审批和评测证据；
- 发布范围和生效时间；
- 发布操作人；
- 回滚目标和原因；
- 当前是否仍可引用。
- 版本替代关系和回滚目标。

### 2.11 审计记录 `AUD`

对关键动作形成不可变更的追踪记录。

业务内容：

- 操作对象及版本；
- 操作人/角色；
- 动作和理由；
- 前状态与后状态；
- 使用的证据和审批结果；
- 时间与关联对象。

## 3. 关系

| 关系 | 基数 | 说明 |
|---|---|---|
| 售后咨询任务 -> 客户上下文 | 1:N | 一次咨询可有多个上下文快照 |
| 客户上下文 -> 检索证据 | 1:N | 一次判断可使用多个有效证据 |
| 知识来源 -> 知识条目版本 | 1:N | 一个来源可支持多个版本；版本必须指回具体来源 |
| 知识条目版本 -> 检索证据 | 1:N | 证据引用具体版本，不引用“知识库”整体 |
| 售后咨询任务 -> 处理建议 | 1:N | 多轮或规则更新后可产生不同版本建议 |
| 处理建议 -> 检索证据 | N:M | 一条建议可引用多个证据，一个证据也可被多次使用 |
| 售后咨询任务 -> 风险升级单 | 1:N | 一次咨询可经历多个风险事件 |
| 售后咨询任务 -> 问题案例 | 1:N | 咨询可暴露一个或多个问题 |
| 风险升级单 -> 问题案例 | 1:N | 高风险事件可转成知识或流程问题 |
| 知识条目版本 -> 评测任务 | N:M | 一个版本可被多次评测，一次回归可覆盖多个版本 |
| 评测任务 -> 发布版本 | N:M | 发布需要引用通过的评测证据 |
| 发布版本 -> 知识条目版本 | N:M | 一个发布版本固定一组知识版本 |
| 任意核心对象 -> 审计记录 | 1:N | 关键动作均产生审计记录 |

## 4. 标识与版本规则

- 每个对象必须有唯一标识；
- 知识、上下文、建议、评测和发布均采用不可变版本；
- 发布后修改知识必须创建新版本，不覆盖原版本；
- 知识版本不得自行声称“已发布”；对外生效状态只能读取 `REL`；
- 知识来源的状态变更必须触发受影响知识版本的复核提示；
- 证据必须能定位到具体知识和来源版本；
- 风险升级单不得因咨询任务关闭而自动关闭；
- 问题案例关闭前必须有关联修复和回归证据；评测通过但未发布时只能停留 `CASE_VERIFIED_PENDING_RELEASE`，不能提前关闭；
- 回滚必须引用目标发布版本和回滚原因。

## 5. 不包含的设计

本文件不定义：

- 数据库表、字段类型和索引；
- API 路由；
- 消息队列和微服务划分；
- 模型、向量库和检索参数；
- 页面布局。
