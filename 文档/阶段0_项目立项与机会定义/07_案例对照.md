# 附件案例对照与反照搬说明

日期：2026-10-22  
对照时点：自主调研与初步产品判断形成之后

## 1. 对照目的

本轮查看附件的目的不是补充“正确答案”，而是：

- 检查我们的机会定义是否遗漏关键业务约束；
- 识别同类案例中值得验证的成熟做法；
- 明确必须避开的页面、文案、视觉、数据和功能结构复用；
- 判断本项目的差异化是否足够，而不是仅换一套界面。

## 2. 案例事实

`[事实]` 提供的 PRD 以某 3C 企业为示例，提出“企业知识管理平台 + FastGPT RAG 底层”的分层方案，包含知识治理、RAG 能力和业务应用。  
`[事实]` PRD 涉及知识库、文档与版本、业务审核、加工验收、检索测试、批量评测、问题案例、权限审计和引擎配置，并给出从草稿到发布的阶段状态。  
`[事实]` 提供的交互原型覆盖运营总览、知识库管理、文档与版本、数据源同步、业务审核、入库任务、处理结果验收、检索调试、批量评测与发布、问题案例、权限与审计、RAG 引擎配置。  
`[事实]` 案例与“企业知识平台 + 通用 RAG 引擎”的行业常见组合接近，因此仅更换品牌、标题或视觉不足以构成新产品判断。

本地文件与阅读证据见 [08_来源清单.md](08_来源清单.md)。

## 3. 与本项目的相同点

以下方向存在合理重叠，说明它们是该问题域的共性，而不是某个案例的独创：

- 知识需要来源、版本、审核和发布；
- RAG 处理结果需要验收；
- 检索质量与最终回答质量需要分开检查；
- 失败问题需要沉淀并回归；
- 权限、审计和引擎边界不可忽略。

这些共性只能作为设计约束，不能作为差异化卖点。

## 4. 本项目的不同起点

| 维度 | 附件案例的起点 | 本项目阶段 0 的起点 |
|---|---|---|
| 业务问题 | 从企业知识平台与 RAG 治理框架展开 | 从多渠道售后“客户诉求 -> 规则适用 -> 证据 -> 下一步动作 -> 结果”展开 |
| 核心对象 | 知识库、文档、处理任务、评测与引擎 | 售后问题、业务条件、有效证据、处理建议、升级与业务结果 |
| 用户价值 | 管知识、可检索、可发布 | 在对话中减少错误口径与重复沟通，同时守住高风险边界 |
| 产品边界 | 平台管知识，引擎管检索生成 | 建议必须理解渠道、时间、商品与风险；高风险先止损；自动化不是首版目标 |
| 成功指标 | 文档、任务、检索与评测质量 | 有效售后问题解决率及口径错误、一次解决、重复联系、知识闭环 |
| 竞品关系 | 以 FastGPT 作为默认底层 | 不锁定具体引擎，底层 RAG 可替换，差异放在领域治理 |
| 参数处理 | 案例包含具体评测样本规模与流程 | 不在缺少真实基线时固定数量、阈值或自动化率 |

## 5. 可借鉴但需重新论证的事项

`[判断]` 以下做法可以进入后续验证清单，但不能直接进入需求：

- 版本与发布状态；
- 审核责任和审计记录；
- 检索调试与批量评测；
- 失败问题的处理状态；
- 测试/生产资源隔离；
- 知识来源与引用展示。

是否保留、以什么粒度保留、由谁负责，必须由真实组织流程和风险分析决定。

## 6. 明确不复用的内容

- 不复用案例页面结构和导航顺序；
- 不复用案例的视觉体系、颜色、图标、卡片样式和布局；
- 不复用案例的文案、命名、示例产品、示例问题和示例数据；
- 不复用其角色权限表、状态机、评测样本数量或发布阈值；
- 不把其功能清单直接转为本项目 P0；
- 不把 FastGPT 绑定为本项目产品定位或默认技术前提。

## 7. 对照结论

`[判断]` 附件案例与现有开源产品共同证明了“知识治理 + RAG + 评测”是必要能力，也提示了本项目容易陷入通用平台同质化的风险。阶段 0 保留“证据、版本、审核、评测、失败闭环”作为必要约束，但核心差异化改为售后业务约束、人工可控、高风险升级、坐席采用和问题解决结果。

阶段 1 重新设计信息架构和状态机时，必须以真实业务流程和任务结果为依据，不能以附件页面作为设计母版。
