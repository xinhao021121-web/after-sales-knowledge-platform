# 问题定义：多渠道消费电子售后知识辅助

版本：V0.1  
状态：阶段 0 草案，待验收  
日期：2026-10-22

## 1. 问题背景

`[事实]` 消费电子售后不是单一 FAQ 问题。相关资料同时包含：

- Apple 官方商店对符合条件的商品提供交付后 14 个自然日退货政策；
- 中国网络等远程交易存在消费者收到商品后七日内无理由退货的法定规则；
- 售后还可能涉及 7 日退货、15 日换货、1 年维修等不同权利路径；
- 保外服务价格因部件不同而不同，最终金额还取决于检测；
- 销售和服务渠道包括 Apple Store、授权经销商、授权服务提供商等；
- 冒烟、异味、鼓包、异常发热、进液和皮肤损伤等问题需要先止损和升级。

来源与核验日期见 [08_来源清单.md](08_来源清单.md)。具体法律适用和高风险口径必须由客户法务/售后负责人复核，本文件不构成法律意见。

## 2. 标准问题陈述

当客户提出一个售后问题时，一线客服需要在很短时间内完成以下判断：

1. 客户实际购买/服务渠道是什么；
2. 商品型号、状态和购买时间是否可核验；
3. 当前诉求是使用指导、退货、换货、维修、渠道责任还是安全风险；
4. 哪套规则适用，是否存在例外或更有利规则；
5. 需要什么证据，下一步由谁处理；
6. 哪些话可以说，哪些承诺不能作出。

`[判断]` 现有知识工具往往帮助人“找到文档”，但没有帮助人完成上述受约束的业务判断。问题不是知识不存在，而是知识无法在服务当下与客户上下文匹配，也无法证明答案为何适用于该客户。

## 3. 用户任务（Jobs To Be Done）

### 3.1 一线客服

“当客户在对话中提出售后诉求时，我要快速知道适用的规则、证据和下一步动作，以便在不作越权承诺的前提下把问题推进到可解决的位置。”

### 3.2 售后专员

“当退货、保修、渠道责任或安全风险存在冲突时，我要拿到完整上下文和可核验依据，以便作出可解释、可审计的处理判断。”

### 3.3 知识运营

“当规则、产品或渠道政策变化时，我要知道哪些知识失效、哪些回答会受影响，以便在发布前完成更新和回归验证。”

### 3.4 客服主管

“当团队出现错误口径、重复联系或高风险升级时，我要看到问题根因和知识闭环情况，以便辅导团队并降低业务风险。”

## 4. 事实、推断与假设

| 类型 | 内容 | 当前依据 | 后续验证 |
|---|---|---|---|
| 事实 | 退货、保修、渠道和安全问题存在不同适用条件 | 官方退货页、法律规定、服务与安全资料 | 法务/业务复核具体口径 |
| 事实 | 不同渠道和售后服务点的责任入口不同 | Apple 授权经销商与地点页面 | 设计伙伴真实渠道清单 |
| 事实 | 公开竞品普遍提供 RAG、工作流、Agent、引用或本地部署 | 五个项目的公开 README | 阶段 1 做实际能力验证 |
| 判断 | 通用“文档问答”不足以完成售后决策 | 售后问题需要渠道、时间、商品状态和风险条件 | 用历史对话和人工标注检验 |
| 判断 | 错误承诺和无依据回答是首要风险 | 退换、保修和安全语境会影响真实权益或人身安全 | 业务访谈、事故记录、真实样本 |
| 假设 | 客服频繁在多个文档、政策页和历史群聊之间切换 | 尚未获得该客户的实际行为数据 | 观察、访谈、日志分析 |
| 假设 | 带证据和条件的建议能提高采纳率与一次解决率 | 尚无本项目实验结果 | A/B 辅助试点 |
| 假设 | 失败案例闭环能降低同类误答复发 | 尚无本项目运营数据 | 连续两类发布周期对比 |
| 假设 | 坐席辅助比消费者端全自动客服更适合首版验证 | 风险与责任边界考虑 | 与业务负责人访谈、低风险试点 |

## 5. 根因分析

### 5.1 知识分散且口径不同

官方 FAQ、平台规则、渠道政策、内部 SOP、服务报价和历史处理记录来源不同，更新时间也不同。简单把文件放入同一知识库，不代表它们对同一商品和渠道同时有效。

### 5.2 业务上下文没有被结构化

同一句“可以退吗”至少隐含商品型号、渠道、签收日期、商品状态、问题类型和诉求路径。缺少这些条件时，检索到的相似文本可能是“错误但相似”的答案。

### 5.3 检索质量与回答责任没有分层

检索命中片段只证明内容相似，不证明答案合法、有效、适用或可执行。产品需要把检索证据、业务判断、建议动作和人工责任分开。

### 5.4 高风险问题与普通 FAQ 混在一条链路

连接故障、退换时效和安全事件的风险等级不同。若统一按“问答”处理，可能错过必须先止损或转人工的信号。

### 5.5 反馈没有回流到知识资产

客服纠正、客户二次咨询、主管抽检和渠道争议往往停留在聊天或工单中，无法形成可追踪的知识缺口、责任人和验证结果。

### 5.6 评测与业务结果脱节

只测“回答看起来对不对”无法证明客服是否更容易解决问题。需要同时观察证据、人工采纳、一次解决、重复联系、口径错误和高风险升级。

## 6. 现有替代方案及其局限

| 替代方案 | 表面优势 | 主要局限 |
|---|---|---|
| 搜索知识库/共享盘 | 实施简单、成本低 | 依赖关键词和人工翻找，难处理同义表达与多条件组合 |
| 客服宏/话术模板 | 输出稳定、培训成本低 | 对新政策、新商品和渠道例外响应慢 |
| 通用文档问答 | 上手快、可引用原文 | 容易忽略渠道、时间和风险约束；缺少发布与回归治理 |
| 直接转售后专家 | 专业判断质量高 | 稀缺人力被大量低风险问题占用，响应不稳定 |
| 纯自动客服 | 可覆盖高峰、降低人力 | 高风险承诺难兜底，错误成本高，知识维护要求更高 |

`[判断]` 首版应把“辅助客服作出可解释决策”作为最小价值闭环，再根据质量证据逐步扩大自动化。

## 7. 业务后果

若问题不解决，可能的后果包括：

- 客服给出不一致或已过期的退换/保修口径；
- 客户在渠道、门店和服务商之间重复往返；
- 可远程解决的问题被过度升级，或必须升级的问题被继续排查；
- 主管无法解释错误来源，也无法判断一次知识更新的影响；
- 自动客服扩大后，错误承诺的规模被同步放大。

## 8. 产品机会

机会不在于再建一个通用 RAG 门户，而在于建立一个“售后决策上下文层”：

- 将知识从“文档集合”变成“带适用范围与生命周期的业务证据”；
- 将问答从“相似片段生成”变成“条件满足后的建议与升级”；
- 将运营从“上传文档”变成“发现问题、修正知识、回归验证、追踪结果”；
- 将评测从“模型回答质量”变成“问题解决质量与风险控制”的组合。

## 9. 验证问题

阶段 1 前应优先回答：

1. 哪类售后问题的咨询量、知识查找时间或错误代价最值得先解决？
2. 客服目前如何确认渠道、时间、商品状态和风险信号？
3. 哪些口径必须由渠道、法务或业务负责人审批？
4. 客户真正用来衡量改善的结果标签是什么？
5. 辅助建议进入现有工作台的哪一步，才不会增加额外操作？
6. 哪些错误属于“不能接受”，哪些属于可提示后继续处理？
7. 现有知识能否支持可追溯证据，还是需要先修复来源和版本？

## 10. 问题边界

本阶段仅定义业务问题和假设，不定义：

- 最终页面结构；
- 切片长度、Top K、模型、温度等技术参数；
- 角色权限矩阵；
- 自动化率和准确率目标；
- 具体采购、供应商或部署架构。

这些内容必须在阶段 1 的业务调研和技术验证后形成。
