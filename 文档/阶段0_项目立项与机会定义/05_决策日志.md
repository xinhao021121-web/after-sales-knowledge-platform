## 修订记录

项目负责人于阶段 0 有条件验收时提出以下修订，已纳入本日志：

- 项目正式定义为公开资料驱动的模拟企业内部项目；
- 明确禁止伪造真实访谈、客户数据和业务结果；
- 将原过细的 P0 场景归并为“售后规则判断、安全风险升级、知识更新与问题闭环”三个验证域；
- 保留业务北极星指标，补充可用于模拟项目验收的代理指标；
- 允许在有条件验收后进入阶段 1A，但阶段 1A 只做需求验证。

## 决策规则

- 决策必须对应业务问题，而不是竞品功能；
- 当前证据不足的事项标记为“暂定”，并保留复审条件；
- 参数、阈值、角色权限和组织流程不得凭经验直接固定；
- 若后续访谈、数据或技术验证推翻依据，应更新本日志而不是悄悄改变方案。

## D-001：首个验证场景选择消费电子售后

**状态**：暂定，待阶段验收  
**决策**：以中国消费电子品牌的售后服务作为企业级 RAG 平台的首个设计伙伴场景。  
**依据**：售后同时具有明确的知识来源、时效条件、渠道路径、下一步动作和业务结果，适合建立可验证评测；原始资料也显示退货、保修、渠道责任与安全处置存在真实区别。  
**未选择**：泛企业知识搜索、销售助手、营销内容生成、全行业客服。  
**代价**：行业垂直会牺牲短期通用性；需要学习品牌渠道与售后规则。  
**复审条件**：若设计伙伴无法提供真实对话、知识责任人、渠道规则或结果标签，则改用能够提供这些条件的目标行业。  
**证据**：[02_问题定义.md](02_问题定义.md)、[08_来源清单.md](08_来源清单.md)

## D-002：初始客户聚焦多渠道消费电子品牌

**状态**：暂定  
**决策**：初始客户不是所有电商商家，而是同时经营自营、平台和经销渠道，且售后服务需要知识治理的消费电子/智能硬件品牌或大型专业零售商。  
**依据**：只有跨渠道和跨时间的规则差异，才能显著体现本项目的业务约束能力；单一渠道小商家可能更适合通用聊天或轻量 FAQ。  
**代价**：客户决策链更长，涉及客服、售后、业务、法务和 IT 多方。  
**复审条件**：如果访谈发现品牌方购买力或数据开放不足，而平台型服务商更愿意合作，可调整首发客户类型。  
**证据**：[01_项目章程.md](01_项目章程.md)、[04_场景清单.md](04_场景清单.md)

## D-003：首版以坐席辅助为主，不以全自动客服为主

**状态**：暂定  
**决策**：P0 在客服工作流内提供建议、证据、下一步动作和升级判断；由人工确认后执行或回复。  
**依据**：退货、保修、渠道责任与安全问题的错误成本较高，而当前尚无可证明的高风险自动处置能力。公开竞品已具备问答与 Agent 构建能力，继续做“会聊天的客服”难以建立信任优势。  
**代价**：价值依赖坐席采用，初始增长不来自无人值守；需要设计低干扰的人机协作。  
**复审条件**：P0 证明低风险场景的答案忠实度、证据覆盖、转人工可靠性和业务结果后，才开放 P1 自动执行。  
**证据**：[04_场景清单.md](04_场景清单.md)、[06_假设台账.md](06_假设台账.md)

## D-004：差异点放在售后业务治理，而非底层 RAG

**状态**：接受为阶段 0 产品方向  
**决策**：将产品核心定义为业务上下文约束、证据生命周期、风险升级、评测和问题闭环；文档解析、向量检索、重排、生成和 Agent 编排优先复用成熟能力。  
**依据**：FastGPT、Dify、RAGFlow、MaxKB、AnythingLLM 的公开材料均已覆盖或支持通用 RAG/Agent 相关能力；其中 MaxKB 已明确面向智能客服和企业知识库。  
**代价**：短期不能以“自研 RAG 引擎”讲故事，需要真正理解售后流程和客户数据。  
**复审条件**：若竞品普遍提供同等业务治理能力并形成采购替代，应重新定义细分客户或交付方式。  
**证据**：[03_竞品调研记录.md](03_竞品调研记录.md)

## D-005：采用“成熟引擎 + 领域层自建”的混合技术方向

**状态**：暂定，阶段 1 技术验证后确认  
**决策**：复用成熟解析、检索和生成能力，自建业务上下文、政策有效期、证据呈现、评测与闭环。  
**未选择**：从零研发通用 RAG 引擎；完全依附某个开源产品做贴牌。  
**代价**：需要维护适配层和供应商替换能力；必须定义接口、评测和安全边界。  
**复审条件**：只有在通用引擎无法满足经用户验证的核心需求，且自研带来的业务收益足以覆盖成本时，才扩大自研范围。  
**证据**：[03_竞品调研记录.md](03_竞品调研记录.md)

## D-007：北极星指标采用有效售后问题解决率

**状态**：暂定  
**决策**：以“有效售后问题解决率”为北极星指标，同时观察口径错误、高风险升级、一次解决率、重复联系率、知识闭环和技术忠实度。  
**依据**：文档数、会话数和问答次数不能代表客户问题被正确解决，且容易激励数量而非质量。  
**代价**：需要业务结果标签和人工抽检，数据建设成本高于单一会话量。  
**复审条件**：若设计伙伴无法提供可核验的结案或纠错记录，应改用可观测代理指标，并明确其局限。  
**证据**：[01_项目章程.md](01_项目章程.md)

## D-008：附件 PRD 与原型只做事后对照

**状态**：已执行  
**决策**：在独立形成行业、用户、价值、范围和指标判断后，再查看附件；仅提取可比较的结构与遗漏，不复用页面、文案、示例数据、视觉或功能结构。  
**依据**：用户明确要求附件不是初始答案；且案例与本项目存在同类定位，直接借鉴会削弱自主判断。  
**代价**：需要额外建立自己的场景与评测逻辑。  
**复审条件**：无需复审；后续仍按反照搬规则执行。  
**证据**：[07_案例对照与反照搬说明.md](07_案例对照.md)

## D-009：不在阶段 0 固定参数、权限和目标阈值

**状态**：接受  
**决策**：本阶段不定义 Top K、切片长度、模型、准确率目标、自动化率、客服人数、会话规模及最终角色权限。  
**依据**：这些选择依赖真实数据、业务流程、风险等级、部署能力和法务评审；当前没有足够证据。  
**代价**：阶段 0 不能给出看似完整的实施参数。  
**复审条件**：阶段 1 获得设计伙伴数据与流程后逐项建立基线，并记录配置依据。  
**证据**：[06_假设台账.md](06_假设台账.md)

## D-010：P0 与 P1 分界

**状态**：暂定  
**决策**：P0 先验证坐席辅助、知识治理、风险升级、评测和失败闭环；消费者自助、自动执行、深度订单/CRM 集成、多品牌多语言和质检培训进入 P1。  
**依据**：P0 必须能以较低集成复杂度验证核心价值；自动化、跨系统执行和消费者直连会同时放大风险与交付范围。  
**代价**：首版无法覆盖“无人客服”或完整售后系统替换场景。  
**复审条件**：P0 的决策质量、风险控制和业务收益达到项目负责人确认的门槛后，再进入 P1 设计。  
**证据**：[01_项目章程.md](01_项目章程.md)、[04_场景清单.md](04_场景清单.md)

## D-011：项目正式定义为公开资料驱动的模拟企业内部项目

**状态**：已接受  
**决策**：本项目的用户、流程、样本和验收均以公开资料和模拟工作场景为基础，不声称实际服务过客户。  
**依据**：导师有条件验收意见；当前项目没有真实访谈、客户订单、客服会话和运营结果。  
**代价**：结论的外部有效性有限，不能替代真实业务试点。  
**复审条件**：若未来获得真实设计伙伴和授权数据，应新建真实试点记录，不能把模拟结论改称真实结论。  
**证据**：[README.md](README.md)、[09_阶段0验收记录.md](09_阶段0验收记录.md)

## D-012：不伪造真实访谈、客户数据和业务结果

**状态**：已接受，作为全项目强制约束  
**决策**：不生成虚假的受访者、引语、客户名称、订单、工单、解决率或收益数据；公开问题只按“公开问法”使用。  
**依据**：模拟项目必须保持证据边界，否则需求验证失去可信度。  
**代价**：无法给出看似精确的市场规模和 ROI。  
**复审条件**：无需复审；获得真实数据时也必须有授权与来源记录。  
**证据**：[06_假设台账.md](06_假设台账.md)、[09_阶段0验收记录.md](09_阶段0验收记录.md)

## D-013：将原 P0 场景归并为三个验证域

**状态**：已接受，用于阶段 1A  
**决策**：P0 统一为售后规则判断、安全风险升级、知识更新与问题闭环三个验证域；原有细分场景仅作为域内测试情境。  
**依据**：导师有条件验收意见；按业务决策类型归并可以避免把功能清单当成产品范围。  
**代价**：部分低风险操作场景不再独立成为 P0 目标，只在规则域内用于对照。  
**复审条件**：阶段 1A 若发现三域无法覆盖核心任务，可增补子场景，但不扩张 P0 验证域数量。  
**证据**：[04_场景清单.md](04_场景清单.md)

## D-014：保留业务北极星指标并增加模拟代理指标

**状态**：已接受，用于阶段 1A  
**决策**：保留“有效售后问题解决率”作为业务北极星，同时用必需追问完整率、规则条件匹配率、有效证据覆盖率、安全升级召回率、不可接受错误逃逸率和问题闭环完整率进行模拟验收。  
**依据**：模拟项目无法获得真实结案和业务收益，但仍需可审计地判断需求与方案质量。  
**代价**：代理指标只能证明模拟覆盖和逻辑质量，不能证明客户价值。  
**复审条件**：真实试点获得业务数据后，重新建立北极星基线，代理指标只作过程监控。  
**证据**：[01_项目章程.md](01_项目章程.md)、[阶段 1A 代理指标标注规则](../阶段1A_用户任务与需求验证/05_代理指标标注规则.md)
