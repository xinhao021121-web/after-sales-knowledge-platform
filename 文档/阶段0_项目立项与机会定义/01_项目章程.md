# 企业级 RAG 知识库平台：项目章程

版本：V0.1  
状态：阶段 0 有条件通过，已按导师意见修订  
日期：2026-10-22

## 1. 项目摘要

### 1.0 项目性质

`[决策]` 本项目是**公开资料驱动的模拟企业内部项目**。它以官方公开资料、开源产品文档和公开用户问题作为研究和验收材料，不声称拥有真实客户、真实访谈、真实业务数据或已发生的业务结果。

`[约束]` 模拟信息不得被包装成真实访谈记录、客服会话、订单记录、客户反馈或运营成效。无法获得证据的内容必须标记为假设、判断或待验证项。

### 1.1 首个验证行业

`[决策]` 首个验证行业选择中国消费电子售后，优先覆盖耳机、可穿戴设备等具有多销售渠道、较长售后周期、明确使用安全边界的产品。

`[判断]` 这个切入点比泛企业知识库更容易形成可验证价值，原因是售后问题具有明确的输入、规则、下一步动作和业务结果，适合建立高质量评测集并追踪误答代价。

### 1.2 初始客户画像

初始客户应同时满足以下条件：

- 在中国市场经营消费电子或智能硬件，提供线上自营店、第三方平台和授权经销等多渠道销售；
- 售后知识同时包含商品使用、退换、保修、渠道责任和安全处置；
- 有专门客服团队、售后专员和知识维护责任人；
- 愿意提供脱敏对话、知识文档、渠道规则及结果标签用于共同验收；
- 能指定业务负责人对高风险口径作最终确认。

`[判断]` 该客户不是“所有电商商家”，而是具有跨渠道责任差异和知识治理需求的品牌方或大型专业零售商。

### 1.3 不使用案例作为初始答案

`[事实]` 附件 PRD 与原型在自主调研和初步方向形成后才被查看。  
`[决策]` 它们只用于检查遗漏、比较治理成熟度和避免重复建设，不作为用户、场景、指标、页面结构或需求的来源。

## 2. 业务问题

`[问题陈述]` 多渠道消费电子品牌的一线客服在处理售后问题时，难以在对话当下快速确认“适用哪套规则、依据是什么、下一步该做什么、何时必须升级”。知识分散、规则随渠道和时间变化、答案缺少证据、错误承诺代价高，导致重复沟通、处理不一致和知识更新无法闭环。

问题定义的完整论证见 [02_问题定义.md](02_问题定义.md)。

## 3. 产品定位

### 3.1 一句话定位

面向多渠道消费电子品牌的售后知识运营平台，用可核验的渠道、时效与安全规则辅助客服给出有来源、可审计的处理建议，并在问题闭环中持续更新知识。

### 3.2 核心价值假设

`[假设]` 如果系统能在客服工作流内给出“带业务条件的答案 + 证据 + 下一步动作 + 升级判断”，同时让知识与失败案例持续迭代，那么品牌可以减少错误口径和重复沟通，提高一次解决能力，并让高风险问题得到更及时的处置。

### 3.3 不做什么

- 不以“能聊天”或“支持 RAG”为价值主张；
- 不把模型生成的内容直接当作退换、保修、赔偿或医疗结论；
- 不在首版替代 CRM、工单、订单、支付或供应链系统；
- 不把单一品牌的产品知识固化成平台能力；
- 不以文档数量、切片数量或模型参数作为业务成果。

## 4. 用户与受益者

| 角色 | 核心任务 | 主要收益 |
|---|---|---|
| 消费者 | 获得一致、可执行且尊重规则的售后答复 | 少重复描述问题，少在错误入口间往返 |
| 一线客服 | 在对话中定位规则、证据和下一步动作 | 缩短查找时间，降低越权承诺风险 |
| 售后专员 | 判断退换、保修、检测和升级路径 | 获得完整上下文与可核验依据 |
| 知识运营 | 维护来源、适用范围、有效期与发布版本 | 及时发现缺口，控制失效知识参与回答 |
| 业务/渠道负责人 | 确认不同渠道的商业口径和例外 | 让政策责任清楚、可审计 |
| 客服主管 | 监控质量、风险与团队辅导机会 | 看见问题根因，而不只是看会话量 |
| AI 运营/评测人员 | 建立测试集、评估变更、追踪失败 | 用证据决定能否发布，而非凭体验判断 |
| 系统管理员 | 管理权限、集成和审计 | 控制数据边界并支持追责 |

角色是任务分工的起点，不等于最终权限矩阵。阶段 1 必须基于真实组织与审批流程确认权限。

## 5. 北极星指标与支撑指标

### 5.1 北极星指标

**有效售后问题解决率（Qualified After-sales Resolution Rate）**

计算口径：

`有效售后问题解决数 / 进入辅助流程且有明确结案的售后问题数`

“有效解决”必须同时满足：

1. 客服已获得与当前商品、渠道、时间和风险上下文匹配的建议；
2. 答案引用了有效知识及可见证据；
3. 客服采纳或按建议完成下一步动作；
4. 在服务记录中未因该建议发生知识性纠错、重复升级或错误承诺。

`[判断]` 使用“率”而不是“次数”，避免仅靠扩大流量取得表面增长；质量口径由人工抽检和业务结果共同校验。

### 5.2 支撑指标

| 维度 | 指标 | 说明 |
|---|---|---|
| 决策质量 | 建议采纳率 | 有资格建议中被客服实际采用的比例 |
| 决策质量 | 高风险问题正确升级率 | 安全、法律、渠道冲突等问题被正确识别并转交的比例 |
| 决策质量 | 口径错误率 | 经人工复核确认的错误退换、保修、渠道或安全口径比例 |
| 客户结果 | 一次解决率 | 客户在约定服务周期内未就同一问题重复咨询的比例 |
| 客户结果 | 重复联系率 | 同一客户、同一售后问题在服务链路内再次咨询的比例 |
| 效率 | 平均处理时长 | 对比使用前后，必须与解决质量共同观察 |
| 知识运营 | 问题闭环时长 | 从发现知识缺口到完成修正、验证和发布的时长 |
| 知识运营 | 有效知识覆盖率 | 被测试问题命中有效知识且有证据的比例 |
| 技术质量 | 证据覆盖与忠实度 | 回答能否被引用证据支持，是否出现无依据补充 |
| 采用程度 | 坐席渗透率 | 目标客服团队中实际使用辅助的比例 |

暂不设定数值目标。阶段 1 需从设计伙伴的历史数据建立基线，再按业务收益、误答风险和实施成本确定目标。

### 5.3 护栏

- 未经授权不得生成退款、赔偿、保修承诺或法律结论；
- 出现安全信号时优先止损与转人工，不以“继续排查”替代风险处置；
- 知识过期、来源失效或渠道不明时，系统必须暴露不确定性；
- 不以平均处理时长改善抵消解决质量或风险指标恶化。

### 5.4 模拟项目代理指标

`[事实]` 模拟项目没有真实客户结案和业务收益，不能直接计算“有效售后问题解决率”。

`[决策]` 保留业务北极星指标作为未来真实试点的方向，并用以下人工可标注代理指标验收阶段 1A：

| 代理指标 | 定义 | 代表的能力 | 局限 |
|---|---|---|---|
| 必需追问完整率 | 已提出的关键追问字段数 / 标注要求的追问字段数 | 上下文识别 | 不代表客户愿意回答 |
| 规则条件匹配率 | 建议中正确使用商品、渠道、时间、状态与例外条件的样本数 / 适用样本数 | 规则判断 | 依赖人工标准答案质量 |
| 有效证据覆盖率 | 回答所需证据均被正确引用且版本有效的样本数 / 应有证据样本数 | 可追溯性 | 不证明客服或客户会阅读 |
| 安全升级召回率 | 应升级且被正确升级的高风险样本数 / 全部高风险样本数 | 风险控制 | 受样本覆盖限制 |
| 不可接受错误逃逸率 | 未被拦截或标记的不可接受错误数 / 全部不可接受错误标注数 | 风险兜底 | 无法覆盖未预见错误 |
| 问题闭环完整率 | 有原因、责任角色、修复动作、回归证据和关闭状态的模拟问题案例数 / 模拟问题案例数 | 知识运营 | 不证明组织真实执行 |

代理指标的分级、标注和冲突处理规则见阶段 1A 的代理指标标注规则。所有目标值在完成模拟基线后确定，不以行业经验直接设阈值。

## 6. 产品范围

### 6.1 P0：三个验证域

原阶段 0 中过细拆分的 P0 场景现归并为三个验证域。后续需求验证、评测和原型都必须围绕这三个域组织：

| 验证域 | 要验证的核心命题 | 覆盖的任务情境 |
|---|---|---|
| A. 售后规则判断 | 系统能否基于商品、渠道、时间、状态和诉求，给出有证据、有条件的处理建议，并识别信息缺口 | 退货、质量问题、保修/维修、渠道责任、连接与使用边界 |
| B. 安全风险升级 | 系统能否在危险信号出现时停止普通建议，优先止损并转交正确责任方 | 过热、异味、鼓包、进液、皮肤损伤、疑似非正品或异常身份 |
| C. 知识与问题闭环 | 系统能否控制知识版本，发现问题、修复、回归并留下审计证据 | 知识更新、渠道政策变化、客服纠错、重复问题、发布回滚 |

P0 的价值不是功能数量，而是验证以下结果：

- 规则判断所需上下文能被识别，缺失时会追问；
- 建议有有效证据，且不会越过人工授权；
- 安全风险优先于规则争论；
- 知识更新与失败案例能形成可验证闭环。

具体业务情境见 [04_场景清单.md](04_场景清单.md)。

### 6.2 P1：扩大价值

- 面向消费者的低风险自助问答，并设置转人工与风险兜底；
- 与订单、物流、售后工单和 CRM 建立更深的上下文集成；
- 在低风险、可回滚的场景中自动执行标准动作；
- 多品牌、多产品线、多语言与经销商知识门户；
- 客服培训、质检辅助和知识内容生成辅助；
- 更细粒度的成本、质量和渠道对比分析。

P1 项目必须在 P0 证明“建议有效且风险可控”后才可进入设计。

### 6.3 非目标

- 不做基础大模型、向量数据库或通用文档解析引擎的研发；
- 不替换 CRM、订单、支付、仓储和传统工单系统；
- 不承担退款、赔偿、保修审批和法律责任判断；
- 不提供医疗诊断或替代专业安全处置；
- 不做面向所有部门的泛化企业搜索；
- 不在无数据支撑时承诺多租户 SaaS、计费、插件市场或全渠道覆盖；
- 不以模型参数、切片数量、知识库数量作为产品成功标准。

## 7. 技术方向建议

`[决策]` 阶段 0 建议采用“成熟能力复用 + 领域层自建”的混合路线：

- 复用成熟的文档解析、检索、重排、引用和 Agent/工作流能力；
- 自建售后业务上下文、政策与有效期模型、证据呈现、评测、治理与工单闭环；
- 保持 RAG/模型供应商可替换，避免把产品价值绑定到单一开源项目；
- 阶段 1 先进行技术验证与数据合规评审，再确定 FastGPT、Dify、RAGFlow 或其他实现选项。

技术判断的依据见 [03_竞品调研记录.md](03_竞品调研记录.md)。本阶段不写代码、不做技术架构定型。

## 8. 成功标准与阶段门禁

阶段 0 完成的判定：

- 目标行业和初始客户有明确纳入/排除条件；
- 至少 3 个公开同类产品有可追溯的事实与产品判断；
- 角色、任务、痛点和场景能对应到业务结果；
- 北极星指标可定义，支撑指标覆盖质量、风险、效率和知识运营；
- P0、P1、非目标边界清楚；
- 假设均有验证方式，未被误写成结论；
- 附件仅用于事后对照，有明确反照搬记录。

进入阶段 1 的条件：本阶段通过项目负责人验收，并获得设计伙伴访谈或数据接入承诺。

## 9. 主要风险与依赖

| 风险 | 影响 | 当前应对 |
|---|---|---|
| 选择的设计伙伴没有足够的跨渠道复杂度 | 验证无法代表目标客户 | 在进入阶段 1 前核验渠道、知识所有权和人工升级现状 |
| 无法获得真实对话与结果标签 | 北极星指标和 ROI 无法验证 | 把脱敏数据和结果标签列为合作前置条件 |
| 竞品快速提供相似能力 | 产品差异化被压缩 | 将竞争点放在业务规则、质量门禁和售后闭环，而非底层 RAG |
| 高风险问题误答造成真实损失 | 用户信任与合规风险 | P0 先辅助、强制证据与升级，不开放自动承诺 |
| 知识所有权与渠道政策不清 | 系统无法判断正确口径 | 要求客户指定业务口径负责人和冲突升级机制 |
| 过早扩展为泛企业平台 | 场景失焦、验证周期拉长 | 阶段 1 前不进入泛知识搜索、营销和多部门平台 |

## 10. 待确认项

1. 项目负责人是否接受“消费电子售后”作为首个设计伙伴行业？
2. 是否接受 P0 以坐席辅助和知识运营闭环为主，而非消费者端全自动客服？
3. 是否能提供脱敏客服对话、知识文档、渠道规则和人工处理结果？
4. 是否有可指定的业务/渠道/法务口径负责人？
5. 是否存在必须优先满足的私有化、等保、审计或数据驻留要求？

以上事项确认前，项目保持阶段 0，不进入信息架构、状态机或原型阶段。
