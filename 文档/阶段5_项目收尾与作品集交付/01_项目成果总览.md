# 项目成果总览

## 项目背景

项目模拟一个多渠道消费电子品牌的售后知识协作场景。公开资料显示，相同售后问题会同时受到销售渠道、签收时间、商品状态、故障表现、安全风险与知识有效期的共同影响。仅靠通用聊天机器人生成一段看似合理的回答，无法解决责任、证据和知识生命周期问题。

项目性质：**公开资料驱动的模拟企业内部项目**。没有真实客户访谈、真实订单、真实客户隐私或生产业务结果。

## 目标用户

- 一线客服：理解诉求、补齐上下文、确认建议；
- 售后专员：处理条件判断、检测和转交；
- 知识运营：登记来源、修复知识、关闭问题案例；
- 客服主管：处理冲突、审批与发布；
- 业务/渠道负责人：批准业务口径；
- 法务/安全责任人：处理 R2/R3 风险和来源撤回；
- AI 评测人员：运行固定任务集、记录质量和失败；
- 系统管理员：管理技术权限，但不能绕过业务审批。

## 核心场景

用户带着一个不完整、可能带风险的售后问题进入。系统先补齐客户上下文，再从有效知识版本检索证据，判断条件和例外；如果命中安全信号，先停机止损，不能进入普通售后；如果没有足够知识，明确拒答并形成案例；如果条件明确，生成有引用、有承诺边界的建议，由有权限的人确认后发送。

## 产品定位

这是一个“售后人员辅助 + 知识治理闭环”的企业工作台，不是面向消费者的全自动客服，也不是单纯的知识库管理后台。

主入口是一线售后工作，知识治理与评测是支撑后台。原因是业务价值发生在“一次咨询被正确、安全、可解释地处理”这一刻，而不是文档被上传这一刻。

## 核心业务流程

```text
ASQ 咨询任务
  → CTX 上下文版本
  → EVD 检索证据
  → ADV 条件化建议
  → 人工确认与发送
  ↘ R2/R3 风险 → ESC 前置止损与升级

问题反馈/评测失败
  → CASE 问题案例
  → CASE_LINK 修复链路
  → KB 知识版本
  → EVAL 回归
  → REL 发布/停止/回滚
  → AUD 审计
```

4. P04 风险队列；
5. P05 风险升级单；
6. P06 知识来源台账；
7. P07 知识与业务审核；
8. P08 问题案例队列；
9. P09 案例与修复链路；
10. P10 评测中心；

### 回归与已知缺陷

- 8 条既有回归语义通过 8/8；
- 固定 27 条包含 17 条正式、8 条回归、2 条保留样例；
- `RET-H09` 首次失败保留为 1/2 保留样例失败；
- 未删除题目、未修改首次失败、未降低阈值。

来源：[R5 新保留样例结果](../阶段4B-2A-R5_单目标检索与质量收口/07_新保留样例首次结果.md)。

### Pro / Flash / 混合路由

固定 27 条、同一检索快照：

- A Pro：语义 25/27，80,819 Token，平均 38.0 秒；
- B Flash：语义 26/27，60,953 Token，平均 14.4 秒；
- C Flash→Pro：语义 26/27，68,060 Token，平均 15.2 秒，回退 5 次。

三组 P0 模型调用和最终失败均为 0，Claim 引用失败均为 0。推荐继续以 Pro 为默认，不启用自动 Flash 路由。
